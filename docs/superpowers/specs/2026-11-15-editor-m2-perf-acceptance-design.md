# 编辑器 M2 性能验收补完设计

日期：2026-11-15

## 意图

在当前 `origin/main` 基线上完成代码编辑器 M2 性能验收的复测与必要优化。先用同机、同负载、成对测量确认已有长行修复（`03307a6`、`9757cb2`）的实际效果，再根据 profile 和计数证据定点修改 `ui/editor`，最后重新测量并诚实更新 `docs/specs/code-editor-m2-report.md`。

目标不是为了让报告“看起来通过”，而是区分真实产品瓶颈、GPU/帧调度噪声和测试环境噪声。

## 目标

- 复测 M2 仍未完成的长单行换行输入门槛：1 MB 单行、换行开启、输入 p95 ≤ 16 ms。
- 复测显示能力相对 M1 及逐项关闭能力的成对退化，确认是否仍有超过 1.10 的项目。
- 复测滚动绝对门槛，并保留与 Monaco 的同场景对照；不把 Monaco 的端到端差距通过改口径隐藏。
- 对超过门槛且可归因于 `ui/editor` 的项目，先补稳定的计数/分配回归测试，再做最小修复。
- 重新运行全量编辑器测试、必要的 race 测试和跨平台 vet，更新报告中的测量日期、数据、结论及仍待人工验收项目。

## 非目标

- 本轮不重写 UI 框架、`ui/text/**` 或平台窗口宿主；用户批准且独立审查通过的 F fence / P retained-copy 候选可修改 `internal/render/gpu/metal/**`，并单独执行 Metal 包测试、race 和编辑器回归。
- 不关闭默认显示能力、不缩小视口、不跳过正确性检查来制造性能数字。
- 不为了追平 Monaco 而无数据地重构 ScrollRegion、GPU 提交或宿主帧调度；只有复测和 profile 明确指向 `ui/editor`，或 F/P Metal 候选已由独立审查证明能在统一 Wait 口径下改善 copy 路径时，才进入优化。
- 不改变 M2 的性能门槛、Monaco 对照规则或内存口径。
- 不把锁屏、IME、Windows 实机等尚未执行的人工项目写成自动化通过。

## 当前事实与约束

- `origin/main` 已包含 M2 编辑器功能、DiffView 和最近的长行/调度修复；工作区当前干净。
- 现有报告的主要未通过项是长单行换行 p95，以及 Monaco 更快时的滚动端到端门槛；显示能力的点估计此前均在 1.10 内，但部分置信区间较宽。
- 现有工具和基准位于 `ui/editor/perf_test.go`、`ui/editor/perf_*_test.go`、`ui/editor/perfab/{arms.sh,run.sh,summarize.py}`。
- 成对测量需在同机、同场景、ABAB 交替、新进程、负载低于 6 时进行；失效轮次作废并重跑。绝对 fps 是离屏吞吐，不冒充实窗 vsync 帧率。
- 代码改动仅限 `ui/editor/**`、用户批准且独立审查通过的 `internal/render/gpu/metal/**` F/P 候选、必要的性能证据和 `docs/specs/code-editor-m2-report.md`；不回退其他会话的改动，也不启动会干扰 `tango-mem` 的 GUI/内存基准。

## 方案比较

### 方案 A：先复测再定点优化（采用）

先运行已有门禁和成对驱动，收集长行、输入、滚动、打开、后台高亮及逐项开关数据；只对超过门槛且 profile 能归因到编辑器代码的热点做最小修改，然后完整复测。

优点是证据链完整、改动范围小，能避免把环境噪声误判为回归；缺点是如果瓶颈在 GPU 等待或宿主调度，本轮可能只能把该项保留为未通过并说明原因。

### 方案 B：只合并现有修复并重写报告

直接把已有性能修复视为最终结果，只补跑报告需要的基准。

优点是最快；缺点是无法证明修复是否稳定达到门槛，也无法对新的超限点做归因，不符合“先复测再优化”的要求。

### 方案 C：以 Monaco 滚动端到端数字为目标继续重构

直接深入 ScrollRegion、GPU 提交和平台帧调度，持续追求 Monaco 的吞吐。

优点是潜在收益最大；缺点是范围会扩大到渲染器/宿主，超出当前 M2 编辑器性能验收边界，也无法在没有 profile 证据时判断投入是否有效。

本设计采用方案 A：方案 B 缺少验证，方案 C 等复测证据证明问题属于编辑器且值得扩大范围后再单独立项。

## 已确认的实施决策

- 正式基线是当前 `origin/main` 的 `9382b0b`；计划 Tasks 1–9 视为已有实现，本轮不重新实现这些功能。
- 正式成对测量避开其他会话的高负载工作，等机器进入相对安静且负载低于 6 的时段；高负载期间只做不影响判定的代码检查或单元测试。
- 用户已批准把 F fence 适配与 P retained-copy 候选作为本轮 GPU 路径的定点修复；两者需保持 F-only/F+P 单变量比较，单列 Metal 原生纹理成本，不把锁屏离屏结果写成实窗验收。
- `go test -race ./ui/editor/...` 全量若因墙钟预算在并行减速下失败，但单独预算测试通过且没有数据竞争，按已知环境限制记录，不为此扩大测试基础设施或改变产品性能门槛。

## 实施顺序

1. **基线确认**：固定提交/测试二进制、生成输入文件、Go/OS/机器信息，确认其他会话没有占用同一 GUI 性能资源。
2. **已有修复复测**：运行 `BenchmarkTypeLongLineWrap`、长行工作/调度测试、百万行输入、滚动、100 MB 打开、TS20k 后台高亮和内存基准；长行至少按计划要求进行多轮 p95 测量。
3. **成对归因**：运行 `ui/editor/perfab/arms.sh` 或其当前等价驱动，覆盖 M1→当前默认、当前默认→`TANGO_EDITOR_PERF_OFF=all`、逐项关闭能力三组；记录每轮负载、p50/p95/p99/fps/open-ms 和中位数比值。
4. **定点分析**：对仍超过 1.10 或长行 p95 超过 16 ms 的场景运行 CPU profile、alloc profile 及现有计数测试；优先检查帧内重复取行/分词/装饰、每帧分配和不必要的整帧重绘。
5. **最小修复**：每项修复先增加稳定的回归测试或计数断言，再修改 `ui/editor`；保持默认行为和正确性不变。
6. **回归验证**：重复受影响的基准和全套 M2 门禁；若瓶颈不在编辑器代码，停止扩大改动，报告剩余原因和证据。
7. **报告收尾**：更新 `docs/specs/code-editor-m2-report.md`，把新数据与旧数据区分，明确通过、未通过、统计上未判定和待人工验收，不提前声称整体通过。

## 验收标准

- `go test ./ui/editor/... -count=1` 通过。
- 改动渲染路径时，`TestViewDamageVerified` 及严格导航测试通过。
- darwin `go build ./...`、`go vet ./ui/editor/... ./examples/editor-demo` 通过；`GOOS=windows` 和 `GOOS=linux` 的编辑器 vet 通过。
- 改动文件 `gofmt -l` 无输出；至少执行一次 `go test -race ./ui/editor/... -count=1`，并如实记录受墙钟预算影响的结果。
- 长单行 p95、M1/逐项退化和滚动对照均用新鲜成对数据判定；任何未达到的门槛保留未通过，不修改门槛或测量口径。
- 只有所有自动化门槛都通过时，报告才写“自动化验收通过”；实窗、IME、Windows 实机仍单列为人工验收。

## 留给实施者的判断

- 若已有修复使长行门槛稳定通过，优先不再改产品代码，集中完成成对测量、报告和回归检查。
- 若长行仍超限，先判断超限来自 CPU 工作还是 GPU 等待/帧调度；只有前者且能在 `ui/editor` 内证明收益时才优化。
- 若滚动端到端仍落后 Monaco，但 CPU 工作已更优且热点在渲染器/宿主，本轮不跨边界修复，保留清晰的后续任务证据。
