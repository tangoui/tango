# 下行轮询通道（down:poll）设计

状态：设计稿，待审 · 2026-11-14

## 1. 意图

Tango 页面收消息（Go→JS）现在只有一条路：`Surface.Send(msg)` 把消息排到主线程，每条消息调一次 `evaluateJavaScript("window.__tango._recv(<JSON 字符串字面量>)")`。消息没有合批，每条都要占一次主线程，载荷还要再 JSON 编码一遍。

2026-11-14 与 Wails v3.1.0 Streams 在同一台 Mac 上交替对比（`/Users/admin/min/ipc-bench/REPORT.md`）：Tango 往返延迟快约 3 倍、上行快 2.4–5.9 倍，但下行明显落后——64 KiB 字节帧 244 对 919 MB/s，1 KiB 小帧 3.4 万对 39 万帧/秒，约 2.3 KB 的 JSON 帧 2.5 万对 9.5 万帧/秒。MinCode 准备从 Wails 迁到 Tango，它的大流量（AI 流式、数据库结果分块、HTTP 流、终端输出）恰好都是 Go→JS，而且大部分是 JSON 帧和小帧。

现有的下行快速通道 `down:scheme`（单个长流式响应）在 Apple 平台上被 WebKit 扣住大块数据，已经停用；而且按规格它只运字节帧，就算能用，也帮不上 JSON 和小帧。

本项目用一条**轮询式下行通道**替换 Go→JS 的整条传输：页面始终挂一个 `fetch` 请求，Go 有消息时用一批消息**结束**这次响应，页面立即发下一个请求。每次响应都会结束，避开 WebKit 扣住流式响应数据的问题；多条消息合成一次响应，不占主线程，也不做二次编码。这是 Wails v3 Streams 在三个桌面平台上已经验证过的思路（只借思路，实现按 Tango 风格自研）。

## 2. 目标 / 非目标 / 反目标

**目标**

- 所有经 `Surface.Send` 发往页面的消息（ipc 的 JSON 帧与控制消息、调用回复、jsapi 事件、应用直接用 `__tango.onMessage` 收的消息）在通道可用时都走轮询通道。
- ipc 的字节帧也走这条通道，作为原始字节，不做 base64，大小不设下限。
- 页面看到的消息顺序与现在完全一致：同一页面内，`Send` 的调用顺序就是 `onMessage` 的回调顺序，不管消息走哪条路。
- 通道不可用或失败时自动退回 `evaluateJavaScript`，不丢消息、不重复、不乱序。页面重载时的行为与现在一致（见 5.5）。
- 第一期只在 macOS 实现并默认开启（需达到第 6 节的门槛）；iOS、Windows、Linux、Android 的接入点在设计里留好。

**非目标**

- 不改上行（`postMessage` 与 `up:post` 保持原样）。
- 不改 ipc 协议语义（帧、序号、信用窗口、控制消息）和 `@tangoui/runtime` 的公开 API。
- 不改 `Surface.Eval` 的对外行为，包括它注释里的承诺“与 Send 保序”（实现方式见 5.9）。

**反目标**（技术上能跑，但出现就算失败）

- 单条小消息的往返延迟明显变差（终端按键回显、普通调用回复变慢）。
- 页面卡住、被遮挡或在后台时丢消息或报 `transport`。
- iframe 或其他来源的页面能拿到通道、读到别的页面的消息。
- 应用需要改代码才能用上。

## 3. 约束（已核实）

- 页面消息全部汇到 `Surface.Send`（`surface.go:311`）：主线程上追加到 `pending`，页面加载完成前暂存，`flush` 时逐条 `Eval(recvJS(msg))`（`bridge.go`）。页面侧是 `coreShim` 的 `window.__tango._recv` → `onMessage` 订阅者。
- `coreShim` 与运行时脚本只注入主 frame；`Surface.Eval` 只在主 frame 执行，可作为可信的下发途径（令牌只经它下发）。
- macOS 的 `tango://` 协议处理器已经异步：请求在 goroutine 里运行，写出端支持 `Flush`，WebKit 停止请求时取消 context（Apple 通道计划 Task 2/3）。iOS 同。
- 通道相关请求由核心 `serveLane`（`lanes.go`）处理，统一走 `laneRequestAllowed` 的来源检查；页面世代号和令牌在 `internal/lane.State` 里，由 runtime-js 的 `hello` 触发新世代。
- 实测：WebKit 对**单个长流式响应**会扣住大块突发数据；对**结束的响应**会完整交付（规格 §6.2 实测补充）。本设计依赖后者，需在真实 WebKit 上重新验证（大批量、突发、长时间运行）。
- `fetch` 到 `tango://app` 受页面 CSP 的 `connect-src` 约束；被拦截时必须退回 Eval（`up:post` 已有同样的启动探测做法，`TestLaneCSPBlocked`）。
- 只有 macOS 能在本机实测；iOS 只有模拟器；Windows、Linux 没有实机。

## 4. 方案取舍

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A. 替换 `Surface.Send` 底下的传输（选定）** | 核心层的轮询通道承载所有页面消息与 ipc 字节帧，Eval 作兜底 | 改动集中在核心传输一层，所有消息都受益；ipc 协议不变；可扩到 Windows/Linux。风险是单条消息延迟，需实测 |
| B. 在 ipc 协议里扩展快速通道 | 让通道包格式装 JSON 帧和控制消息，由 Router 选路 | 要改 ipc 的控制消息排序规则；jsapi 事件等非 ipc 消息不受益 |
| C. 只把 Eval 合批 | 同一轮排队的消息合成一次 `evaluateJavaScript` | 便宜，但二次编码和主线程占用仍在，达不到"替换"的目的；可作为 A 的兜底路径改进，不作为主方案 |

用户 2026-11-14 选定 A，并明确 JSON 帧和小帧都要走新通道。

## 5. 已定的设计

### 5.1 分层

- **核心（根包 `*tango.Surface`）** 拥有下行传输：消息序号、待送队列、轮询通道状态、退回 Eval。`Surface.Send` 不再直接 Eval，而是交给传输层。
- **`internal/lane`** 增加 `down:poll` 的服务端：持有挂起的请求、按批写出、处理确认。`down:scheme` 由 `down:poll` 取代（见 5.7）。
- **`ipc.Router`** 不改协议。`down:poll` 作为下行通道报告给 Router 后，字节帧经 `SendBinary` 交给同一个传输队列，与字符串消息按同一顺序发出；`BinaryMinSize` 对 `down:poll` 为 0。
- **平台后端** 只报告能力（本页面能否用 `down:poll`：协议处理器能否异步、能否挂起请求）。macOS 第一期报告；其他平台先不报告，行为不变。
- **页面侧（`coreShim`）** 负责轮询循环、按序号重排、交给 `onMessage` 订阅者。这一层不依赖 runtime-js：只用 `__tango.onMessage` 的应用同样受益。

### 5.2 握手与令牌

- 轮询通道属于核心，不等 runtime-js 的 `hello`。页面加载完成（`SurfaceLoaded`）后，核心用 Eval 向主 frame 下发一个内部消息：通道开启、世代号、一次性令牌、端点路径。令牌只经 Eval 下发，iframe 拿不到。
- 每次页面加载（含重载、导航）开始新的下行世代：旧世代挂起的请求立即结束，旧令牌作废。
- 与 runtime-js `hello` 驱动的 `lane.State` 世代的关系由实现者统一：可以合并成同一个世代号，也可以各自独立，但页面重载时两者都必须换代，且 `up:post` 不受影响。

### 5.3 序号与顺序

- 核心给每个下行世代内**真正发出**的每条消息（字符串或字节包）分配递增序号，从 1 开始。Eval 兜底路径也带序号。
- `coreShim` 按序号交付：缺号时先缓存后面的消息，等缺的那条到达。这样 Eval 与轮询响应即使在 WebKit 内部交错到达，订阅者看到的顺序也与 `Send` 一致。
- 切换时机：通道开启前、开启过程中、失败后，消息走 Eval；收到页面第一个轮询请求后，后续消息改走轮询队列。

### 5.4 轮询请求与响应

- 页面请求：`GET tango://app/__tango/lane/poll?gen=<世代>&tok=<令牌>&ack=<已交付的最大序号>`。同一时刻每个页面只有一个在途请求。
- Go 侧：有待送消息时立即用一批消息结束响应；没有时挂起，直到有消息或到达挂起上限（建议 25 s，到时返回空批，页面立即重发）。
- 一批的上限：按字节（建议 4 MiB）和条数（建议 4096）取先到者，剩下的留给下一次轮询。
- 响应体格式（二进制，大端），带明确的 `Content-Type: application/octet-stream` 与 `X-Content-Type-Options: nosniff`：

```
batch := firstSeq:u64 | count:u32 | item*count
item  := kind:u8 | len:u32 | payload[len]
kind  := 0 字符串消息（UTF-8，即原来 Send 的 msg）
       | 1 字节包（现有通道包格式：count:u16 | frame*，交给 runtime-js 的下行通道处理）
```

- 页面解码后，字符串消息照原样交给 `onMessage` 订阅者，字节包交给 runtime-js 的下行通道处理入口。少了"JSON 字符串字面量包一层"这一步。

### 5.5 确认与重发

- Go 保留已写进响应、但页面还没确认的那一批消息。页面下一次轮询带的 `ack` 确认之前的消息，Go 随即丢弃。
- 页面报告通道失败时（`fetch` 出错、状态码不是 200、解码失败、CSP 拦截），经 `__tango.post` 的内部消息告诉 Go 失败和已交付的最大序号。Go 把这一世代改回 Eval，从该序号之后重发所有未确认的消息，之后的新消息也走 Eval，直到下一个世代。
- **字节包的兜底**（设计者的决定）：未确认的字节包退回 Eval 时，用 base64 包在一条带序号的内部消息里，交给 runtime-js 的同一个字节包入口。这是核心传输层的事，不改 ipc 协议，ipc 也不需要补发。
- **页面重载**（设计者的决定）：与现在完全一致。现在页面处于已加载状态时，`Send` 立即 Eval 给当前页面，页面若随后自己重载，这些消息随旧页面丢失；从导航开始到新页面加载完成之间的 `Send` 暂存在 `pending`，加载后交给新页面。新设计照此划分：新世代开始（导航开始）时，旧世代队列里已排队但未写出的消息和未确认的消息都丢弃；之后的 `Send` 进 `pending`，新页面加载、新世代从序号 1 开始后再发。

### 5.6 兜底与开关

- 兜底路径就是现在的 Eval，改为带序号；顺带把同一轮的多条消息合成一次 Eval（方案 C），作为兜底路径的改进。
- 关闭开关沿用现有约定：`TANGO_IPC_LANES=0`、`Options.DisableFastLanes` 关闭所有通道。macOS 的 `TANGO_IPC_LANES_DARWIN` 取值（设计者的决定）：

| 取值 | `up:post` | `down:poll` |
|---|---|---|
| 未设置（默认） | 开 | 达到第 6 节门槛后开；未达到前关 |
| `1` / `all` | 开 | 开（未达门槛前用于测试） |
| `up` | 开 | 关（排障用） |
| `down` | 关 | 开（排障用） |
| `0` / `false` / `off` | 关 | 关 |

`all` 不再表示开启 `down:scheme`（该通道删除），并且与 `1` 一样在任何构建里都生效。门槛达不到时照样合入，默认关闭，用 `1` 打开。
- 页面不是来自资源来源（例如直接加载开发服务器 `http://localhost:5173`）时不开启，与现有快速通道一致。

### 5.7 与现有通道的关系

- `down:poll` 取代 `down:scheme`：后者在 Apple 上停用、其他平台没有接入，删除其服务端与 runtime-js 模块，`TANGO_IPC_LANES_DARWIN=all` 的含义随之调整。
- `up:post` 不变。
- 平台专属下行通道（Android 的 ArrayBuffer 消息、Windows 共享内存）仍在规格中，与 `down:poll` 并存时的优先级由实现者在接入那些平台时决定；本期不涉及。

### 5.8 页面侧行为

- 轮询循环在页面卡住（长同步任务）时自然停顿，Go 侧消息继续排队；页面恢复后一次取走。不得因此报 `transport`（沿用规格 §5 的卡顿规则，`laneStall` 场景）。
- 页面被遮挡、最小化、在后台时，消息仍需送达（与现在 Eval 一致）。**保底**（设计者的决定）：Go 侧看门狗——有消息待送、但超过一个阈值（建议 1 s，按实测调整）没有轮询请求到达时，把这些消息按序号改走 Eval，下一个轮询到达后恢复。这样不依赖平台上报窗口可见性；序号机制保证顺序。需实测 WebKit 对后台页面 `fetch` 的节流，确认看门狗不会在正常前台流量下误触发。

### 5.9 `Eval` 与 `Send` 保序：栅栏

用户 2026-11-14 决定保留 `Surface.Eval` 的承诺（“in order with Send”），用栅栏实现：

- 轮询通道开启时调用 `Eval`，核心在下行队列里插入一个栅栏项（kind 2，载荷为栅栏编号），占一个序号；脚本本身不进队列。
- 页面按序号交付到栅栏时停下，把栅栏编号经内部消息告诉 Go，此后的消息先缓存不交付。
- Go 收到后用 `evaluateJavaScript` 执行原脚本，脚本末尾追加放行调用（`__tango` 内部的放行函数，带栅栏编号）。页面收到放行后继续交付后面的消息。
- 多个 `Eval` 连续排队时各自一个栅栏，按序执行。
- 栅栏只在轮询通道开启时使用；走 Eval 兜底时消息和脚本本来就在主线程上依次执行，不需要栅栏。退回 Eval 的过程中，未放行的栅栏对应的脚本按序号补执行，不跳过、不重复。
- 脚本执行出错（抛异常）也要放行：放行调用放在 `finally` 里，或由 Go 在 `evaluateJavaScript` 的完成回调里补发放行。
- 页面重载时未执行的栅栏随旧世代丢弃，与现在“Eval 给即将离开的页面”的效果一致。
- 测试：`Send(a)`、`Eval(脚本记录 b)`、`Send(c)` 连续调用 N 轮，页面记录的顺序必须严格是 a、b、c；脚本抛异常时后续消息照常交付；大量消息积压时 `Eval` 等到前面的消息交付后才执行。
- 延迟：`Eval` 在通道开启时多一次页面→Go 的往返。第 6 节的门槛不包含 `Eval` 延迟，但要在报告里记录。

## 6. 验收门槛（macOS，默认开启的条件）

在同一台机器上交替运行，沿用 `ipc-bench` 的六项测试（Tango 侧在 `examples/duplex -bench` 基础上补上小帧与 JSON 两项），与改造前的 Tango 和 Wails v3.1.0 对比：

- 下行三项（64 KiB 字节帧、1 KiB 小帧、约 2.3 KB JSON 帧）都不低于 Wails v3.1.0 同场景中位数。
- 64 B 往返平均延迟、分批 p99 不比改造前的 Tango 差超过 10%；上行吞吐不下降。
- 现有快速通道的真实 WebKit 场景全部通过：页面重载不泄漏、页面卡住 6 s 不报错、CSP 拦截退回、iframe 拿不到令牌、故障注入后退回不丢帧。新增：大批量突发（如 64 MiB 连续下行）多次运行不丢、不卡住。

达不到延迟门槛时的退路：通道空闲且只有一条小消息待送时走 Eval，积压时才走轮询（序号机制保证顺序）。
