# 每个窗口独立 UI 线程（共享层 + macOS）设计

日期：2026-11-18
状态：待用户批准（审阅问题已答复）
范围：`ui`、`uihost`、`internal/platform`（契约）、`internal/platform/darwin`、`internal/render/gpu/metal`、`internal/render/quartz`、`sys/dialog`、受影响的示例和文档。iOS、Android、Windows、Linux 各自单独设计，不在本文范围。

## 1. 意图

macOS 上，应用在前台切换（激活、失去焦点）时，AppKit 会把主线程占住 34–109 ms。Tango 的整条出帧链路（事件处理、页面函数、布局、绘制、渲染、上屏）都在主线程上，这段时间画面完全停住；mygo 基于 WebKit，合成在独立进程里，不受影响。

实测（2026-11-18，`outputs/tango-link-fallback-20261118/`、`/tmp/offmain-spike/`）：

- 网格场景每 2 秒切换一次前台：Tango 超过 20 ms 的帧从 0.17% 升到 1.67%，P99 从 17.6 ms 升到 21.1 ms；mygo 不变。
- 主线程探针：每次切换主线程被占 34–109 ms；同时段 Tango 自己的焦点、生命周期回调都不超过 2 ms，出帧本身 2.6–4.9 ms。卡顿来自 AppKit/系统。
- 一次性原型：后台线程用 CAMetalLayer 出帧，切换前台时主线程同样被卡 71 ms，但系统报告的上屏间隔 P99 一直是 16.67 ms；主线程出帧时 P99 是 33.3 ms。
- 计时器兜底（主线程上补帧）只把 P99 从 20.96 降到 20.17 ms，因为主线程被卡时计时器也跑不了。

结论：只有让出帧链路整条离开主线程，才能彻底解决。

## 2. 目标、非目标、反目标

目标：

1. macOS 上每个 uihost 窗口的页面函数、布局、绘制、渲染、上屏都在该窗口自己的 UI 线程上运行，主线程被 AppKit 占住时，窗口照常出帧。
2. 共享层（`ui`、`uihost`、平台契约）支持"UI 线程不是主线程"，其他平台保持"UI 线程 = 主线程"，不改行为。
3. 开发构建里，在错误线程上修改页面状态会立刻报错并指出改法。
4. 仓库内示例和文档按新约定改好。

非目标：

- 其他平台的独立 UI 线程（各自单独设计）。
- 多窗口之间共享状态的框架级同步（应用自己负责，本设计只提供投递接口）。
- 改动 WebView 窗口（`App.NewSurface` 的网页窗口）的线程模型。

反目标（即使能跑也算失败）：

- 现有应用的数据竞争在正式构建里悄悄发生、开发构建里也没有任何提示。
- 主线程空闲、不切前台时，任何场景的帧耗时、P99、内存比现在变差（以 gate11/gate13 为基线）。
- 输入到画面的延迟变差（以 b25960c、1ef979c 的编辑器打字测量为基线）。

## 3. 方案

考虑过三种做法：

- **A 每个窗口一条 UI 线程，整条出帧链路搬过去（采用）**：唯一能彻底解决的做法，原型已证实 Metal 路径可行。
- **B 页面留在主线程，只把渲染和上屏搬走**：主线程被卡时页面函数跑不了，动画没有新内容，只能重复上一帧，不算彻底解决，否决。
- **C 平时主线程出帧，卡住时切到后台线程**：两边要能驱动同一个页面，同步过于复杂，否决。

线程约定，用户在两种里选了 **②：页面代码和主线程、其他窗口真正并行**，不用全局锁轮流运行（①）。理由：并行度最高，多个窗口可以同时出帧；代价是不兼容变更，用开发构建检查把隐藏的数据竞争暴露出来（用户同意）。

平台顺序（用户确认）：共享层 + macOS → iOS → Android → Windows → Linux。做完一个平台就让该平台默认使用独立 UI 线程，没做完的平台暂时保持"UI 线程 = 主线程"，各平台行为暂时不一致（用户同意）。

## 4. 新的线程约定

### 4.1 线程角色

- **主线程**：应用的事件循环。运行 `App.OnReady`、`App.Post` 投递的函数、窗口创建和关闭、AppKit 回调（输入、尺寸、焦点、无障碍查询、输入法查询）、系统对话框、菜单、托盘。
- **窗口 UI 线程**：每个 uihost 窗口一条，从 `uihost.Open` 返回前启动，窗口关闭后退出。运行该窗口的页面函数、`ui.Runner` 的全部方法和回调、渲染器和呈现器。锁定在一条操作系统线程上（`runtime.LockOSThread`），因为 Metal/Core Animation 的部分对象要求同一线程使用。

### 4.2 对外接口变化

- `uihost.Open`、`uihost.Attach` 仍然在主线程调用。`Open` 返回的 `*ui.Runner` 归窗口 UI 线程所有；`Attach` 本期保持"UI 线程 = 主线程"（见 §10）。
- 新增 `(*ui.Runner).Post(fn func())`：在该窗口的 UI 线程上、两帧之间运行 fn，任何线程可调用，按调用顺序执行。在 UI 线程上调用时排到当前帧之后，不会立刻执行。窗口关闭后丢弃。`Post` 之后自动请求一帧。
- `(*ui.Runner).Invalidate`、`InvalidateAt` 在任何线程调用都安全（现在已是如此，保持）。
- `App.Post` 不变，含义明确为"在主线程上运行"。文档改为：要改页面读取的状态，用 `Runner.Post`；要调用必须在主线程的系统接口，用 `App.Post` 或 `tango.Await`。
- `ui.Window` 接口的实现方（uihost 的 `window`）全部在 UI 线程上被调用；需要主线程的操作（设置光标、输入法客户端、剪贴板、窗口状态、开始拖动窗口、关闭窗口）由 `window` 内部转发到主线程，调用方感知不到。
- 不兼容变更写进 CHANGELOG 和 `docs/release.md` 的迁移说明，附改法示例。

### 4.3 哪些窗口使用独立 UI 线程（设计者的决定，见 §10）

- macOS 上 uihost 独立窗口（`uihost.Open`）全部使用，不论渲染路径：Metal、native、CPU（含透明、Material 窗口，以及 GPU 失败后降级到 CPU 的窗口）、非 arm64。CPU 路径和 native 路径用的是同一种机制（在 UI 线程上修改 `CALayer` 的 contents 并显式提交事务），验证一次覆盖两者。
- CPU 路径不再依赖 AppKit 的 `updateLayer`：在独立 UI 线程模式下，CPU 帧和 GPU 帧一样由 UI 线程上的显示链接驱动，`Present`/`PresentDamage` 在 UI 线程上设置图层内容。
- 运行中切换渲染器（native 因按键升级到 Metal、`TANGO_RENDERER=auto` 升级、GPU 失败降级）需要主线程的步骤（`UseMetalLayer`、`UseCoreGraphicsLayer`）由 UI 线程用 `tango.Await` 同步请主线程执行；只发生一次，可以等待。
- `uihost.Attach`（在 WebView 窗口上叠自绘层）本期不迁，保持"UI 线程 = 主线程"。
- 同一个 `ui.Runner` 支持两种线程模型：绑定独立 UI 线程，或"UI 线程 = 主线程"（其他平台、`Attach`、`tan dev` 宿主）。模型在 `Open`/`Attach` 时按窗口确定，之后不变。

### 4.4 开发构建检查

- 开发构建（`tango_dev` 标签，`tan dev` 和测试默认开启）在以下入口检查调用者是否在本窗口的 UI 线程上，不是就 panic，信息写明"在 UI 线程之外修改了页面状态；用 Runner.Post 投递"：
  - `Runner` 的公开方法（`Post`、`Invalidate`、`InvalidateAt`、`Close` 除外）。
  - `ui.Context` 的状态读写入口（`State`/`Ref` 一类按 key 取得的状态、`Set*`、`Invalidate`）。具体入口列表由实现者从 `ui` 包整理，原则是"页面函数之外能拿到并修改的东西"。
- 线程判定用 goroutine 标识（UI 线程的 goroutine 在启动时记录），正式构建不编译这些检查。
- 只检查绑定了独立 UI 线程的 Runner。没有绑定的（无头 `ui.Driver`、测试直接驱动的 Runner、`NewRunner` 之后尚未 `Attach` 的阶段、其他平台、WASM playground）一律不检查，现有测试不用改。
- 应用自己的变量（例如 ledger 的 `l.notice`）框架无法检查；文档和迁移说明要明确这一点，并建议应用用 `go test -race` 跑一遍。

## 5. 共享层设计

### 5.1 窗口 UI 线程与事件转发

uihost 为每个窗口创建一个 `uiThread`：一条锁定 OS 线程的 goroutine，持有一个任务队列（输入事件、尺寸变化、焦点变化、`Runner.Post`、出帧请求），循环取任务执行。

平台回调（`CanvasSink`）在主线程上被调用，uihost 把它们变成任务入队后立即返回，不等 UI 线程处理：

- `CanvasInput(ev)`：入队，触发出帧请求。
- `CanvasResized(w, h, scale)`：入队，见 5.4 的同步出帧。
- `CanvasFocus(f)`：入队。
- `CanvasFrame()`：见 5.2。

`Runner.HandleEvent` 等现有方法在 UI 线程上执行，不改内部逻辑。

### 5.2 出帧调度

现状：平台的 `CanvasFrame()` 在主线程上同步完成整帧（包括 `Present`）。

改为：

- 平台契约新增可选能力 `platform.CanvasThreaded`（名称由实现者定），声明"这个 canvas 允许在非主线程上出帧和上屏"，并提供平台侧在 UI 线程上的显示链接/定时回调。macOS 实现它；其他平台不实现，uihost 走现有主线程路径。
- 实现了该能力的平台：显示刷新回调直接投递到窗口 UI 线程（macOS 用每个窗口自己的 `CADisplayLink`，加到 UI 线程自建的 `NSRunLoop`/`CFRunLoop` 上；或用 `CVDisplayLink`/`CAMetalDisplayLink` 回调再投递——两者的取舍见 6.2）。
- 节拍规则不变：每个刷新周期最多一帧，静止窗口不出帧；`frameAtOnce`（b25960c，停顿后立即出帧）和 `InvalidateAt` 定时器语义保持，在 UI 线程上实现。

### 5.3 互相等待的规则（防死锁）

- **主线程从不无限期等待 UI 线程。** 只有两处主线程会等：改尺寸（§5.5，上限 1 个刷新周期）和应用退出（上限 1 秒）。
- UI 线程可以等待主线程（对话框、`tango.Await`、`ReadClipboard`、切换渲染器）。等待期间 UI 线程把自己标记为"正在等主线程"；主线程看到这个标记时，改尺寸直接跳过等待（靠图层左上对齐兜底），不会形成环。
- 关闭（`OnClosed`）不等待：主线程把窗口标记为已关闭、不再投递任务，然后立即返回；UI 线程在下一次运行（或从对主线程的等待返回）时发现已关闭，自己释放渲染器、呈现器后退出。窗口原生对象在 UI 线程退出后由主线程释放（UI 线程退出时投递一个释放任务给主线程）。
- 应用退出：主线程通知所有 UI 线程退出，最多等 1 秒；超时的 UI 线程放弃其资源（进程即将结束）。

### 5.4 阻塞式系统调用（对话框）

`sys/dialog` 的各函数在 UI 线程上被调用时：把请求转给主线程（`tango.Await` 语义），调用它的 UI 线程阻塞等待结果；这期间这个窗口不出帧，其他窗口照常。对话框的父窗口仍是该窗口。

其他会阻塞的 `sys/*` 接口（通知权限请求等）按同样方式处理，实现者需逐个核对 `sys/` 下的包，凡是要求主线程且会阻塞的都走这条路。

### 5.5 改变窗口大小

要求：拖动改变大小时不能露出拉伸或错位的旧画面（canvas-surface.md 现有要求）。

做法：`setFrameSize:`/`viewDidChangeBackingProperties` 在主线程上触发时，主线程把尺寸变化入队并等待 UI 线程出完新尺寸的一帧（有上限，建议 1 个刷新周期，超时就先返回，靠图层的左上对齐兜底）。只有改尺寸这一种情况主线程会等 UI 线程。

### 5.6 嵌入 WebView（`ui.NativeView`）

现状：`embeds.sync()` 每帧在主线程上按布局摆放 WebView（`setFrame:`）。

改为：UI 线程每帧结束时生成"本帧 WebView 摆放列表"，投递给主线程执行摆放；画布画面和 WebView 位置可能差一帧。验收要求：滚动时 WebView 与周围自绘内容的错位不超过 1 帧，且静止后对齐。如果实测错位明显，回退方案是：有 NativeView 的窗口不使用独立 UI 线程（在设计实现中保留这个开关点）。

### 5.7 主线程上需要立刻得到答案的判断

AppKit 有几类回调要求主线程当场给出答案，而答案依赖 UI 状态。做法统一为：UI 线程每帧结束时发布一份只读的"UI 状态快照"给主线程，主线程用最新快照当场判断（最多晚一帧）：

- 窗口快捷键：快照包含"焦点是否在可编辑文本上""是否在输入法组字中""是否在录制快捷键"。匹配仍在主线程按现有规则进行，命中的按键不入队（不到达 UI），和现在的语义一致；快捷键回调 `fn` 仍在主线程运行。
- 窗口拖动区域（自绘标题栏）：快照包含本帧的拖动区域列表；鼠标按下落在区域内时，主线程直接开始拖动窗口，不经过 UI 线程。`ui.Window.StartWindowMove` 保留，作为快照未覆盖时的补充（UI 线程投递，主线程用最近一次鼠标按下事件执行）。
- 无障碍命中测试：已经读平台层的树副本，不变。
- 光标形状、第一响应者：UI 线程决定后投递给主线程，最终状态生效即可。

### 5.8 无障碍与输入法

二者已经是"UI 每帧把快照推给平台层，AppKit 查询时读平台层的副本"，不回调 UI：

- 无障碍树：`SetAccessibilityTree`/`UpdateAccessibilityNodes` 从 UI 线程调用，平台层在内部把快照交给主线程（加锁或投递）。AppKit 的查询读主线程上的副本。
- 无障碍动作（`AccessibilityAction`）由主线程收到后入队到 UI 线程。
- 输入法：`SetTextInput(enabled, caret)` 从 UI 线程调用，平台层转主线程；`firstRectForCharacterRange` 读主线程上已有的光标位置，不变。

### 5.9 主题、语言、内存等全局通知

`follow.go`、`memory.go`、`contrast.go`、`motion.go` 现在在主线程上直接改 Runner。改为在主线程收到系统通知后，用 `Runner.Post` 投递到各窗口的 UI 线程。

### 5.10 关闭

见 §5.3：主线程不等待，UI 线程自己释放后退出。`Runner.Post` 在关闭后丢弃任务。

### 5.11 开发与自动化宿主

- `uihost/automation_dev.go`（`TANGO_AUTOMATION`：Find、Perform、Snapshot、Tree、Input）：迁到新模型。它在主线程上收到请求后，用 `Runner.Post` 投递到 UI 线程执行、用通道等待结果（自动化工具本身在其他线程等，主线程不阻塞）。E2E 测试依赖它，必须一起改。
- `tan dev` 热重载宿主（`remote_dev.go`）：保持"UI 线程 = 主线程"模型，本期不改。

## 6. macOS 设计

### 6.1 Metal 路径

- `CAMetalLayer` 的 `nextDrawable`、命令提交、`presentDrawable` 在 UI 线程上执行（原型已证实可行）。
- `presentsWithTransaction` 保持 NO。
- 层的几何属性（`frame`、`contentsScale`、`drawableSize`）：`drawableSize` 由 UI 线程在出帧时设置；`frame` 和 `contentsScale` 仍由主线程在尺寸变化时设置（现有 `syncHostedLayer`），UI 线程读取尺寸时使用主线程快照。
- `metal.NewPresenter` 的"只能在主线程"改为"在创建它的 UI 线程上使用"。

### 6.2 显示链接

- 首选：在 UI 线程上建自己的 run loop，把 `NSView.displayLink` 创建的 `CADisplayLink` 加到这个 run loop 上（macOS 14+）。需要验证：视图的 displayLink 能否加到非主线程 run loop 上并正常回调。
- 备选：`CVDisplayLink`（回调在 CoreVideo 线程，再投递给 UI 线程）。
- 实现者先用原型验证首选方案；不行再用备选。最低系统版本沿用现状（macOS 14+ 用 displayLink，更低版本用定时器）。

### 6.3 native 路径（Core Animation 图层，`internal/render/quartz`）

- 图层树的修改在 UI 线程上用显式 `CATransaction`，提交后在非主线程上调用 `CATransaction.flush()`（原型已证实提交间隔不受主线程卡顿影响）。
- 未验证：提交的图层内容是否按时显示到屏幕上（原型用录屏核对，工具本身漏帧，无结论）。实现阶段的第一项任务就是用真实 Tango 窗口验证（方法：系统上屏回调或对比 Metal 图层的上屏时间）。
- 如果 native 在后台线程上屏不可靠：数据窗口（`ui.ContentData`）在独立 UI 线程模式下改走 Metal，记录内存代价（约多 70 MB），并请用户确认。

### 6.4 主线程上保留的工作

窗口创建、`NSView` 层级、`NSTrackingArea`、光标设置、第一响应者、输入法客户端激活、窗口状态（最小化、全屏）、窗口拖动、关闭——全部仍在主线程。UI 线程需要它们时投递到主线程，不等待结果（光标、输入法位置这类"最终状态"类调用），或用 `tango.Await` 等待（极少数需要返回值的）。

## 7. 验收

判定规则：所有"不比现在差"都以同批 AB/BA 交替测量、全部样本保留为准。P99 差距在 1 ms 以内（mygo 帧间隔精度）视为持平；超过 20 ms 的帧比例差距在 0.3 个百分点以内视为持平；内存、CPU 差距在 5% 以内视为持平。超出就算变差，由设计者报告用户决定，不得自行放宽。

性能（同批、全部样本保留、负载低、无人操作屏幕）：

1. 网格每 2 秒切换前台：Tango 超过 20 ms 的帧比例与 P99 不比安静时差超过测量误差，且不比 mygo 差。
2. 安静场景（grid、list，gate11/gate13 流程）：内存、CPU、P99 不比现在差。
3. 编辑器打字输入到画面延迟（min-78 的 GUI 矩阵）：不比现在差。
4. 拖动改变窗口大小：无拉伸、无错位帧（截屏核对）。

正确性：

- `go test -race` 覆盖：多窗口同时出帧、`Runner.Post` 与输入交错、关闭时的竞争。
- 开发构建检查：在错误线程修改状态的测试必须 panic，在 UI 线程上不 panic。
- 仓库内所有示例在开发构建下启动、操作一遍不触发检查。
- 无障碍（VoiceOver 读取、动作）、输入法（中文组字）真机验证。
- 嵌入 WebView 示例（`examples/webview-embed`）滚动错位 ≤ 1 帧（逐帧截屏，比较 WebView 边缘与相邻自绘内容的位置）。

## 8. 风险

- **native 后台上屏**：未验证，见 6.3 的回退。
- **显示链接放到非主线程 run loop**：未验证，见 6.2 备选。
- **多窗口并行**：GPU 设备、字体缓存、图片缓存等全局资源要能被多条 UI 线程同时使用；实现者需逐个核对 `ui/text`、`internal/render/gpu`、`ui/paint` 的全局缓存是否线程安全，不安全的加锁或改为每窗口一份。
- **第三方应用迁移**：不兼容变更，靠开发构建检查和迁移说明降低风险。

## 9. 留给实现者决定

- `CanvasThreaded` 等新接口的具体名称和方法签名。
- `uiThread` 任务队列的数据结构。
- 开发构建检查的完整入口列表（按 4.3 原则整理）。
- 改尺寸时主线程等待的上限（建议 1 个刷新周期）。
- 全局缓存是加锁还是改为每窗口一份（按热点实测决定）。

## 10. 用户已决定的事项

- 线程约定选 ②：页面代码与主线程、其他窗口真正并行，用 `Runner.Post` 投递（2026-11-18）。
- 开发构建加线程检查（2026-11-18）。
- 平台顺序：共享层 + macOS → iOS → Android → Windows → Linux；做完的平台先默认启用，其他平台暂时保持现状（2026-11-18）。
- native 上屏不再用原型单独验证，放到实现阶段用真实窗口验证；不行时数据窗口改走 Metal，内存代价请用户确认（2026-11-18）。
