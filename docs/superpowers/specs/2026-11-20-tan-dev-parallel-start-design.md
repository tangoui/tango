# tan dev 可选并行启动

## 目标

MinCode 临时对照的五对热样本均改善，端到端中位数从 3.16 秒到 2.96 秒；冷样本波动较大，不承诺冷启动收益。将并行做进桌面 `tan dev`，现有项目默认行为不变。

## 方案选择

采用 `tan.json` 的 `frontend.parallelDevBuild: true` 显式开启。默认并行虽然覆盖所有项目，但会破坏依赖前端生成文件（例如 `go:embed`）的项目；只改 MinCode 脚本则需绕开或重复 `tan dev` 的进程管理。字段名和对不适用模式的处理是本设计的实现选择。

## 行为与边界

- 仅当桌面 `tan dev` 自己负责启动 `frontend.dev` 时生效；未设置或为 `false` 仍走原串行路径。`-url`、`frontend.devURL`、静态前端、自绘无前端、移动端、发布构建都保持原行为。
- 依赖安装成功后才进入并行阶段。前端进程启动后，等待其就绪信号的同时执行原有 Go 构建；两侧成功后才允许启动普通应用或热重载宿主与 worker。保留现有就绪协议（首个有效 URL、超时和退出处理），不新增 HTTP 探活。
- 启用方须确保前端命令不生成或更新首次 Go 构建依赖的文件。保留稳定应用路径、签名、热重载能力判定及中途回退；不引入构建产物复用，也不改构建次数或标签。
- 90 秒是自前端进程启动起等待 URL 的期限，不限制 URL 就绪后的 Go 构建时长。前端在首次启动交接前报错、退出（包括已报 URL 后退出）或未按时报 URL，均结束本次启动，取消并回收进行中的构建。Go 构建失败不启动旧产物；前端仍存活时保持等待 Go 文件编辑后重试，前端退出仍须打断等待。应用或热宿主启动前复查已观测到的前端退出和取消；不承诺消除操作系统异步退出与 `Start` 之间的竞态，也不改变首次启动完成后的前端退出策略。用户取消时回收本轮启动的前端和构建进程树，并收齐等待任务。
- 同步 JSON Schema 和中英文配置文档。先用隔离 MinCode 夹具开启并复测，再更新 MinCode 项目配置；不提前让旧版 `tan` 读取新字段。
