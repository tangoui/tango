# UI 组件极限性能：两层基准与按热点优化 设计

状态：待用户审批
日期：2026-11-16

文档审核修订：2026-11-16。补齐跨框架统一工具链和默认渲染后端的记录要求；项目实施状态保持上述草稿状态。

## 1. 意图

把 Tango 自绘 UI（根 `ui` 包约 180 个组件入口）的性能压到极限。用户没有具体痛点，要求先给全部组件建基准，再按实测热点排优先级、分批优化。

停止标准（用户定）：**同场景下比 MyGo 和 NSGo 都快，且各自领先至少 50%**（CPU 不超过对手的一半，口径见 6.3）。MyGo、NSGo 都没有的组件，用"最接近的对手场景"对比，同时满足一组硬预算。

## 2. 目标

- 每个根 `ui` 组件入口都有统一的进程内基准，覆盖四个场景：首次构建、静止帧、交互帧、大数据（仅集合类组件）。
- 每个场景记录：单帧 CPU 耗时、分配次数与字节数、局部重绘面积（脏矩形并集 / 视口面积）。
- 按热点分批优化，每批用固定二进制、交替 A/B 证明收益，不放宽任何现有测试与像素断言。
- 对有对手的场景（三家都有的组件，或"就近对手场景"），用进程外跨框架 runner 证明 Tango 比 MyGo、NSGo 都快。
- 输出一份逐组件状态表：场景、Tango 数据、对手数据、硬预算是否达标、是否已达停止标准。

## 3. 非目标

- 不改渲染器后端（Metal / D3D11 / GL / macOS 原生 CoreAnimation 路径）、内存常驻策略、终端、代码编辑器内核。这些由其他会话负责（`perf/macos-native-renderer`、`perf/default-idle-memory`、`feat/terminal-perf`、`perf/editor-acceptance`、`perf/mygo-10pct`）。热点落在这些区域时，记录证据并转交，不在本项目里改。
- **可以改**（用户定）：文字 shaping 与测量缓存，ui 核心的构建、布局、节点生命周期、指纹。这些区域也有其他会话在动（全模块性能审计 `perf/all-modules-20261116`、`fix/ui-node-retention`），所以开工前先看对方 worktree 和最新的 origin/main，基于 origin/main 做，冲突由本项目负责解决；不改对方 worktree。
- 不改组件公开 API、默认值、视觉（Ant Design 6.7 / Pro v6、Element Plus 2.14.8、shadcn v4 基线不变）。
- 不追求内存指标领先；内存只作为不回归护栏（见 6.5）。
- 不在 Windows / Linux / 移动端做实机对比（本机只有 macOS/arm64）；跨平台只保证编译与单测通过。
- 子包 `ui/mobile`、`ui/chart`、`ui/graph`、`ui/editor`、`ui/terminal` 不纳入组件分母（已各有基准或有专门会话）。

## 4. 反目标（技术上"更快"但算失败）

- 靠降低视觉质量、跳帧、延迟呈现、减少可访问性语义或关闭局部重绘校验换来的数字。
- 只在合成基准里快、在跨框架实测里不快的改动被宣称为达标。
- 对手程序写得刻意低效（不按该框架惯用写法），或 Tango 场景比对手做的事少。
- 优化后某个组件行为变化、RTL / 三主题 / 高对比度 / 无障碍审计回归。

## 5. 约束

- 仓库 `github.com/tangoui/tango`，Go 1.27；遵守 AGENTS.md 设计基线与 `ui/AUTHORING.md`。
- 测量环境：Apple M4 / macOS 26.6；只在 1 分钟负载 < 6 时采信；工作站有其他会话，必须记录背景负载并剔除受干扰轮次。
- 对手版本固定：MyGo v0.9.0（`github.com/egoist/mygo`），NSGo 固定到一个 commit（实现时选当前主分支并写入结果）。
- 三方统一完整 Go 工具链版本，初始固定 `GOTOOLCHAIN=go1.27.3`、`CGO_ENABLED=0`、`GOOS=darwin`、`GOARCH=arm64`。若所选对手 commit 要求更高版本，须统一提升三方版本并全部重编、重测；不得让自动工具链仅升级一方后混用旧结果。
- 每轮保存源码版本、完整构建命令与环境、输入/场景标识、二进制 SHA-256 和 `go version -m` 输出；核验三方工具链、CGO、架构及发布参数一致后，才能采纳比较。仓库曾因 Go 1.27.2/1.27.3 混用撤回比例，见 [第四批报告](../../performance/2026-11-16-modules-batch4.md)。
- 不照搬 MyGo / NSGo 代码（用户规则）；跨框架 runner 自研，只借测量方法。对手场景程序按各框架惯用写法实现。
- 提交：作者 `tango <903300326@qq.com>`，不加 Co-Authored-By；不 `git add -A`；推送前问用户。

## 6. 方案与已选方案

### 6.1 方案对比

| 方案 | 做法 | 取舍 |
|---|---|---|
| A 先做跨框架场景再优化 | 每个可比组件写三份程序，进程外量 CPU/帧/内存 | 直接对准目标，但一轮测量很慢，且无法定位热点 |
| **B 两层基准（已选）** | 进程内 Go 基准找热点、做 A/B；进程外跨框架 runner 做最终判定 | 迭代快、可定位，结论以进程外实测为准；要维护两层 |
| C 只压公共管线 | 用 gallery 大页面压构建/布局/指纹/绘制 | 普惠但漏组件自身热点，无法逐组件证明比对手快 |

用户选 B。

### 6.2 第一层：进程内组件基准（`ui` 包内）

- 新文件 `ui/perf_components_test.go`（或按组件分组的 `perf_*_test.go`），以表驱动方式为每个组件入口登记一个 **场景夹具**：
  - `build(c *Context)`：渲染一个"典型"实例（按 gallery 对应页的默认用法：典型属性、典型文字长度、中文与英文混合）。
  - `interact(d *Driver)`：该组件最常见的一次交互（悬停、点击、键入一个字、展开浮层、切换标签、拖动一步等），可以为空（纯展示组件则用"文字/数值变化一次"代替）。
  - `large(n int)`：仅集合类组件（Table、List、Tree、Select、Cascader、Transfer、Menu、Tabs 等）提供，n ∈ {1 000, 10 000, 100 000}。
- 四个场景各一个 `Benchmark` 子测试（`BenchmarkComponents/<组件>/<场景>`），统一窗口 1440×900、scale 2，主题矩阵默认 antd，另加 element/shadcn 作为周期性检查。
- 指标：
  - CPU：只计 **构建 + 布局 + 绘制命令生成 + 指纹**（"NoRaster"口径，与 GPU 宿主在 CPU 上付出的一致）；CPU 光栅化单独一列仅供参考，不进停止判定。
  - 分配：`b.ReportAllocs()`。
  - 局部重绘：用现有 `DamagePresenter` 测试设施，报告脏矩形并集占视口比例；交互帧若超过组件包围盒的 2 倍，记为"重绘过大"热点。
  - 静止帧（本人决定）：`Runner.Frame()` 每次被调用都会构建并 Present，跳过空闲帧靠宿主看 `NeedsFrame()`。所以"静止"的含义是：`Settle()` 后无输入时 `NeedsFrame()` 为 false，且没有多余的 Invalidate 或动画唤醒。残余 CPU 记两项：一是判定 `NeedsFrame()` 的开销，二是宿主被强制调一次 `Frame()`、内容没变时的开销。后者属于"无变化帧"，也纳入优化，但不改 Runner 和宿主之间的约定。
- 首次构建的缓存口径（本人决定）：预算按**热缓存**算，即进程内字形、shaping、主题派生和图标缓存已经预热，每次迭代新建 Runner 再构建。冷启动单独一列，只报告不判定，因为冷启动的热点在字体缓存，这块不在本项目范围内。
- 组件分母与覆盖检查（本人决定）：分母以源码为准。测试扫描根 `ui` 包里所有导出的 `func Xxx(c *Context, ...)` 组件入口，每个入口必须在夹具表中登记，或写明"不适用"理由（纯布局件、纯包装件）。不解析 `ui-coverage.md` 的文字。`ui-coverage.md` §6.1 排除的 CodeBlock、JSONView、Dock、StatusBar、TitleBar、NotificationCenter、HotkeyInput 和 Chat 族（BubbleList、Conversations 等）**纳入**本项目。LogView 归 `perf/memory-logview` 会话，只建基准，不在本项目里优化。
- 热点排名工具：`internal/cmd/uiperf`（新）运行上述基准、生成 CPU/alloc profile，并输出按"超出硬预算倍数 × 被多少组件共享的调用栈"排序的热点表（Markdown + JSON）。

### 6.3 第二层：进程外跨框架 runner（独立模块）

- 位置：`bench/ui/`，独立 `go.mod`（依赖 MyGo、NSGo、Tango 本地 replace），不进入 Tango 产品模块与 API golden。
- 自研 runner（借鉴既有报告方法，不复制 NSGo runner 代码）：
  - 按第 5 节固定统一工具链、CGO 和目标平台，三方都用 `-trimpath -ldflags "-s -w"` 发布构建。核验构建清单后使用新进程，首帧就绪信号后静置 3 s，采样 10 s；
  - 指标：进程 CPU、合成器（WindowServer）CPU 增量、二者之和、帧回调间隔 p50/p99、实际更新帧率、physical footprint；
  - 窗口尺寸与渲染路径（本人决定）：每个场景用固定窗口，沿用既有跨框架报告的尺寸（如 counter 360×260、quotes 560×860、list 480×800），新场景按组件自然大小定。Tango 用**默认策略**，启动前清除继承的 `TANGO_RENDERER`，不强制后端。窗口面积只影响初始选择：小窗口可优先使用原生 CoreAnimation，持续慢帧/全帧后仍可能转向 GPU，初始化或设备失败也可能回退 CPU。不能按面积推定整个采样期的后端。
  - 在 UI 主线程于首帧就绪、静置结束、采样开始/结束及帧回调中记录 `uihost.Renderer`；发生路径变化时保存时间戳。结果表注明实际后端与切换事件。主结果保留完整采样期及切换成本；稳定阶段可另列，不得只挑切换后的低成本样本，也不能把混合路径标成单一 native/Metal 场景。MyGo 用它的 GPU 自绘 `ui` 模式，不用 webview 模式；NSGo 用默认原生绘制，并同样记录实际路径与回退。
  - 每场景三框架交替顺序运行，至少 5 轮；1 分钟负载 ≥ 6 或测试进程外有突发 CPU 的轮次剔除，保留原始数据。
- **"快"的判定**（用户定"至少领先 50%"，口径与编辑器 10% 项目一致）：同场景下，Tango 的（进程 CPU + 合成器 CPU）各轮中位数 **≤ 对手中位数 × 0.50**，而且双方各轮的四分位区间不重叠；同时实际更新帧率不低于对手，帧间隔 p99 不高于对手。三项都满足才算"更快"。对 MyGo 和 NSGo 分别判定，两家都满足才达标。
- 剩余差距如果有证据表明来自渲染器后端（例如合成器 CPU 或渲染提交占了大头，而构建、布局、绘制命令这部分已经不到对手的一半），就标为"受限于渲染器，已转交"，附 profile 证据，不算达标也不算失败。
- 场景清单：
  - **直接可比**：三家都有的组件（Button、Input、TextArea、Checkbox、Radio、Switch、Slider、Select/Combobox、Tabs、Menu、Tooltip、Popover、Dialog/Modal、Toast/Message、List、Tree、Table、DatePicker、ColorPicker、Progress、Pagination 等，实现时以三家源码核对出最终交集表）。
  - **就近对手场景**：Tango 独有组件映射到对手最接近的组合，例如 Cascader → 对手 combobox + 多列 list；Transfer → 两个 list + 按钮；ProTable → table + 查询表单；Tour → popover + 遮罩。映射表写入结果文档，每行说明为什么认为"等价"。
  - 每个场景定义"每帧做什么"（例：每帧改 10% 数据、每帧滚动一行、每秒打开/关闭一次浮层），三家实现相同的工作量。

### 6.4 硬预算（本人提议，适用于所有组件，含无对手的）

窗口 1440×900、scale 2、Apple M4、NoRaster 口径：

| 场景 | 预算 |
|---|---|
| 首次构建（单个典型实例） | ≤ 0.5 ms；浮层类（Modal、Drawer、Dropdown 面板）≤ 2 ms |
| 静止帧 | 不触发 Present；残余 CPU ≤ 0.02 ms |
| 交互帧 | ≤ 2 ms；整页 gallery 场景 ≤ 4 ms |
| 大数据交互帧（100 000 项） | ≤ 4 ms，且与 1 000 项相比增长不超过 1.5 倍（只渲染可见区） |
| 局部重绘 | 交互帧脏区 ≤ 组件包围盒 2 倍 |

预算在第一批基线出来后可由我收紧（只收紧不放宽），变化写入结果文档。

### 6.5 护栏（每批都必须满足）

- 正确性：`go test ./ui/... ./examples/ui-gallery/...` 全过，包括 `TestGalleryForcedHintsVerified`（GPU 严格局部重绘）、无障碍审计、RTL 镜像检查、文字对比度。
- 内存：footprint 与分配不回归超过 5%（跨框架 runner 与进程内 B/op 都看）。
- 跨平台：Windows / Linux / wasm 编译通过。
- 不放宽任何既有断言或计时门槛。

### 6.6 迭代流程（每批）

1. 用 `uiperf` 生成热点表，选本批目标：优先"多个组件共享的公共管线热点"，其次"超出预算倍数最大的单组件热点"。
2. 每个优化：先写能证明行为不变的测试，再改；进程内固定二进制交替 A/B 5 轮，收益 ≥ 10% 或分配显著下降才保留，否则回滚。
3. 每批结束跑第二层 runner 上受影响的场景，更新逐组件状态表。
4. 若热点落在非目标区域（渲染器后端、内存常驻策略、终端、编辑器内核），只记录证据并转交对应会话。热点在文字、核心管线时直接改，改之前确认对方会话没有正在改同一函数。

停止：某个组件的全部场景都满足以下两条时，标为完成：
- 有对手的场景，按 6.3 的口径同时领先 MyGo 和 NSGo 至少 50%；
- 满足硬预算。

所有组件都完成，或者剩余项都已证明受限于渲染器后端等非目标区域（附证据）时，项目结束。
