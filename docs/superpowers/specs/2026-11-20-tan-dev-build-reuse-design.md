# tan dev：复用首次构建产物

## 目标与范围

默认桌面 `tan dev` 会先构建 worker，再检查产物能否进入热重载模式。不支持时，普通启动路径又用相同的开发构建参数编译一次。本次只去掉首次启动回退时的重复构建，不改 CLI 参数、开发构建标签、前端启动顺序、发布构建或移动端，也不跨会话缓存产物。

## 方案选择

- **采用：复用首次构建产物。** 仍以真实二进制判定热重载能力；不能热重载时，使用刚构建成功的同一产物启动普通开发会话。对现有语义影响最小。
- 不采用：构建前扫描依赖。每次多一道检查，而且依赖图不能完全代替对最终二进制的判定。

## 行为

- 首次构建成功、但产物不支持热重载时，将该可执行文件放到普通开发会话的稳定路径。macOS 仍准备原来的 `.app` 并签名；Windows 和 Linux 保留各自的可执行文件名与权限。随后由现有普通循环启动，保持工作目录、参数、环境及窗口状态配置。
- 只复用**当前会话刚成功构建**的产物，并且只用于普通循环的第一次启动。安置产物失败时，记录原因并走原有构建路径；若最终安置、打包或签名失败，不得启动缓存里的旧程序。取消时清理临时文件，不开始新的构建。
- 支持热重载的应用继续走原路径。`-hot=false`、启动后的文件变更重编，以及热重载会话运行途中退出热重载模式，都维持现有行为。普通会话重编失败时，仍保留正在运行的应用。
- 实现时拆开“构建可执行文件”与“准备普通启动产物”；交接文件优先采用同目录临时文件后替换，保留可执行权限，避免半写入文件被启动。具体内部函数与测试夹具由实施计划确定。

## 验收

- 回归测试记录真实或替身 `go build` 调用：首次非热重载回退只构建一次，普通启动使用该次产物；首次构建失败、交接失败、签名失败或取消时，不启动旧程序；文件变更后正常重编。另验证支持热重载和 `-hot=false` 的路径不变。
- 使用同一 MinCode 夹具、Go 工具链和构建标签做改前/改后对照。冷组每轮使用独立空 Go/Vite 缓存，不计依赖下载；热组两边先预热，再交替采样，分别报告中位数和范围。终点是主界面挂载并完成一次前后端调用，另列 Go 构建次数和各阶段耗时。真实窗口采样按共享机器时段协调，保持两组焦点条件一致。
- 已有单次冷缓存样本到界面可用为 115.85 秒、三次热缓存中位数为 4.77 秒；其中第二次构建分别耗时 11.58 秒和约 0.25 秒。这些是基线观测，不是承诺的节省值。
