# 模块性能第三批执行计划

执行方式：延续已批准的全模块计划，在已有隔离分支直接实施，不重复请求设计批准。

**Goal:** 减少绑定调用和资源路径的临时分配，保留所有接口、错误、JSON 及 HTTP 行为。

## 约束与方案

- 保留标准 JSON 解码、自定义 UnmarshalJSON、错误顺序、null/空数组行为；不用自行解析 JSON 或借用超出解码回调生命周期的输入切片。
- 绑定按注册的参数个数预留临时 RawMessage 容量，将 Context 前缀和参数装入同一个调用切片。精确的 `[]`/`null` 跳过不必要的空参数解码，其他输入保留标准解码。
- 资源路径顺序遍历分段，避免 Split 切片；已有根斜杠时直接清理原路径。保留清理前的穿越检查和 fs.ValidPath，不增加文件缓存。
- 不修改共享测试接收器来改善生产性能数字；生产分配与测试输出捕获成本分别说明。
- IPC AppendPacket 已零分配，ParsePacket 返回独立帧描述切片；本批无已证明值得更改接口的热点，保持源码并记录审计结果。
- 所有性能测量串行；只有前后负载均 <6 的轮次可进入耗时比较。不终止其他会话任务，不无限等待负载。

## 任务与验收

- [x] 记录 bind/asset/ipc 的原始二进制、CPU/分配 profile 和补充代表负载。
- [x] 绑定：新增分配回归（普通相加最多10次、仅Context最多3次、Context+整数最多8次），在旧代码实际失败；再做最小优化。
- [x] 绑定：用旧实现对照普通/Context/变参/嵌套/自定义解码/非法输入的返回值、错误和调用次数；验证返回数据不复用、并发参数不串扰。
- [x] 资源：新增规范化绝对路径零分配回归，在旧代码失败；再修改清理逻辑。生成输入对照旧实现，并通过 HTTP 的穿越/SPA/HEAD/Range/条件响应边界验证。
- [x] 各运行至少5轮固定二进制交替 A/B；负载门槛不满足时明确保留速度未验证，不以高负载数据声称收益。
- [x] 相关包测试/race、全项目/CLI 测试、vet、格式和 diff check；一次独立静态审查。
- [x] 更新覆盖表和第三批报告，提交到优化分支，不推送远程。

## 实际验证记录

- 定点测试、race、vet、格式和 diff check 已通过；独立静态审查无确认问题。
- 初次本批矩阵各5轮（20次），全部因负载门槛不满足排除耗时；分配结果保留，未声称速度已验证。
- 仅 Context 和带空白的空调用曾暴露额外分配，修复后普通预算通过；带空白路径保持原分配。分配预算使用 !race，race 的额外反射分配已对照旧实现确认；功能/并发测试不排除 race。
- 批末完整 Go/CLI 测试通过（546.74 秒，171 包输出逐一核对）；全项目/CLI vet 通过。
- 总计60次测量，只有绑定4对、资源2对满足负载门槛，未达到每模块5对；耗时验收保持未完成，不发布加速比例。

## 审查重点

- 自定义 JSON 解码失败不能调用服务；语法、参数数量和类型错误的先后次序保持一致。
- 参数和 Context 不跨调用共享；返回的 slice/map/RawMessage 仍由每次调用独立拥有。
- 根路径、相对路径、重复分隔符、点段、Unicode/非法 UTF-8、NUL 和反斜杠必须保留原处理结果。
- 路径穿越在 Clean 之前拒绝；Range/HEAD/If-Modified-Since 仍交给 ServeContent，动态文件仍每次打开。
- 未优化的 IPC、HTTP 响应捕获成本和未满足负载门槛的数据不能宣传为已优化完成。
