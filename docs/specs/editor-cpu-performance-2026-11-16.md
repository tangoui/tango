# 编辑器第二轮性能优化实测（2026-11-16）

基线为第一轮已合并的 `a4abb09`。保持现有 Ant Design UI、编辑语义、完整高亮、小地图、缩进参考线、撤销和换行功能。

## 改动与依据

- 小地图直接合成为不可变的预乘 RGBA 图片，省掉渲染器的第二份图片分配和转换。像素逐字节对照原 NRGBA + image/draw 路径，包括透明 RGB、不同 alpha、1×/2×字形和非整数高行距。
- 小地图条带请求复用按视口大小增长的临时缓冲，绘制结束清空旧行引用，缓存图片与 token 继续独立持有。
- 缩进参考线使用排版阶段已有的整行文字；换行续行重复使用模型文字，跳过视图区域，空文字/合成行继续使用原快照读取。
- 回溯规则按需共享当前行后缀的 rune；ASCII 或每字节一个 rune 时不建字节索引表。ASCII 匹配/捕获偏移直接使用原值，Unicode、非法 UTF-8 和越过整体匹配的前瞻捕获仍保留转换。没有改变语法、超时、降级策略和公共 API。

## 整帧对比

Apple M4 / macOS arm64 / Go 1.27.2 / GOMAXPROCS=10。1920×1080 逻辑尺寸、2× 离屏 Metal、2 万行 TypeScript、预先完成全文高亮，`TANGO_EDITOR_PERF_OFF` 为空。每项 300 次操作，旧/新二进制紧邻交替 5 轮，并交换先后顺序；下表为各指标分别取 5 轮中位数。局部重绘复用原画面，和实际应用使用同类 Retainer 路径；完整重绘保留原历史基准。

| 场景 | 整帧 ms：前 → 后 | Runner.Frame CPU ms：前 → 后 | 临时分配 B/op：前 → 后 | 分配减少 |
| --- | ---: | ---: | ---: | ---: |
| 2 万行输入（局部重绘） | 1.848 → 1.772 | 1.218 → 1.192 | 613,543 → 409,101 | 33.3% |
| 2 万行滚动（局部重绘） | 2.554 → 2.418 | 0.913 → 0.867 | 454,040 → 309,964 | 31.7% |
| 2 万行输入（完整重绘） | 4.040 → 4.445 | 1.510 → 1.563 | 629,660 → 428,290 | 32.0% |
| 2 万行滚动（完整重绘） | 4.837 → 4.440 | 1.228 → 1.129 | 442,127 → 292,640 | 33.8% |

这些是操作到离屏 GPU 完成的耗时，不是键盘到屏幕的物理延迟，也不是显示器 FPS。CPU 列只统计 Runner.Frame，不包括之前派发事件的耗时。

时序结论保持保守：局部输入约快 4.1%、局部滚动约快 5.3%；完整输入反而约慢 10%，其 GPU 等待中位数从 2.554 → 2.897 ms，CPU 段也略增 3.5%。共享机器负载变化明显，早期将四项一起交替运行时曾显示局部输入快约24%、完整滚动变慢约21%；分项紧邻复测没有复现同样幅度。因此不能声称所有场景都更快；临时分配下降约32–34%是更稳定的收益。完整输入耗时的差异仍受负载干扰，不能断言其回归完全来自 GPU。

## 超长行、大文件与微基准

额外旧/新交替 3 轮：百万行中段局部输入与 1 MB 中英混合单行自动换行输入各100次；100MB 文件打开每轮1次（文件来自温热页缓存）。

| 场景 | 整帧 ms：前 → 后 | Runner.Frame CPU ms：前 → 后 | 临时分配 B/op：前 → 后 |
| --- | ---: | ---: | ---: |
| 1 MB 超长行换行输入 | 8.078 → 7.325 | 3.040 → 2.244 | 1,903,189 → 1,813,777 |
| 百万行中段输入 | 4.516 → 4.409 | 3.654 → 3.617 | 690,450 → 459,503 |
| 100 MB 文件打开 | 70.108 → 75.048 | 19.440 → 18.790 | 250,797,216 → 250,722,480 |

超长行 CPU 段中位数减少约26%；百万行输入约持平。打开文件没有稳定提速，3个单次样本不足以作速度结论，也不能代表冷磁盘读取。

| 微基准 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 小地图合成至渲染准备（256列条带） | 约31.5 µs，131,200 B，4次分配 | 约16.8 µs，65,600 B，2次分配 |
| 40个可见行的缩进参考线 | 约14.0 µs，69,472 B | 约3.28 µs，5,216 B |
| 128字符短行反复尝试回溯规则 | 约47.7 µs，39,693 B | 约36.5 µs，约5,900 B |
| ASCII前瞻捕获偏移 | 592 B，10次分配 | 528 B，9次分配 |

微基准耗时对系统负载敏感，主要证明删除了哪类重复工作。真实20k行 TS fixture 的 lexer 分配约8.98 →8.72MB，耗时约28ms，未建立稳定吞吐提升。曾尝试整行 rune +索引一律复用，导致真实TS fixture分配增加，已经拒绝该方案，采用按需后缀策略。

## 两轮累计分配收益

为避免把不同工作量的数字相乘，又用最初 `a9ba605` 的保存二进制和本轮二进制，按原来100次操作/项交替5轮。与上面的300次表分开解读：

| 场景 | 最初临时分配 | 两轮优化后 | 累计减少 |
| --- | ---: | ---: | ---: |
| 输入 | 1,120,798 B/op | 520,963 B/op | 53.5% |
| 滚动 | 953,164 B/op | 316,403 B/op | 66.8% |

这仍是每操作累计分配，不能理解为进程RSS按同样比例下降。

## 完整重绘输入的追加调查

额外用Go overlay分别移除本轮词法改动、移除条带改动，保持工作区不变，按1000次输入、4个变体、3轮轮换顺序复测。变体间的耗时仍随系统负载明显变化，没有定位到可重复的单一代码退化。为区分Runner.Frame墙钟区间与真正CPU消耗，又按1500次输入交替3轮，使用子进程rusage记录user+system CPU（包含该测试进程初始化）：

| 轮次 | 基线实际CPU秒 | 本轮实际CPU秒 |
| --- | ---: | ---: |
| 1 | 4.035 | 2.747 |
| 2 | 2.201 | 2.283 |
| 3 | 2.179 | 2.004 |

各轮变化方向并不一致，GPU等待可从约3ms变到十余ms。没有将最后较快的一轮替代前面较慢的结果，也没有把rusage进程CPU当成物理输入延迟。现有数据支持降低临时分配和超长行路径CPU成本，不能支持普通完整重绘输入的统一提速结论。保留两项实现，因为像素/语义不变、分配收益明确，且没有稳定复现某一项引入的退化；更严格的时序结论需要空闲、隔离的测试机器。

## 持续操作与验证

启用完整功能，输入1200次（每40次含一个Enter）、来回滚动1800次。检查每个输入阶段的精确内容、字节数和行数，每个滚动事件必须实际移动视口，且小地图字符、参考线、lexer和已高亮的位图必须存在。通过一次缺少输入派发的受控变异，确认测试会在400键时拒绝无效工作量。

GC 后 Go HeapAlloc（不包含完整GPU/驱动常驻内存）：

- 预热约22.87 MiB。
- 400/800/1200键后约48.73 /52.62 /56.32 MiB，保留真实撤销历史和图片缓存。
- 再经过600/1200/1800次滚动后约43.11 /43.14 /43.14 MiB；此测试观察到平台期，不等于证明所有工作负载无泄漏。

- 编辑器及子包、示例完整回归通过（12个包，editor 76.112s）。
- 仓库短模式回归通过（129个有测试的包；完整 gallery 主题文字扫描按CI约定另行运行，本轮未重复）。
- regex / monarch 全量竞态检查通过（6.224s /19.487s）；小地图、缩进参考线、像素与重绘相关竞态检查通过（134.657s）。
- 正常构建的分配预算、逐字节像素对照、Unicode / 非法UTF-8 / 前瞻捕获 / 嵌入语言 / 超时 /降级回归通过。竞态构建的 Go sync.Pool 会故意随机丢弃条目，因此只跳过该构建中短行匹配的数值分配预算；正常构建预算继续执行，所有语义与并发检查保留。
- vet、示例构建、gofmt、git diff --check 通过。
- 独立只读审查未发现生产正确性缺陷；要求补上的持续工作量断言已用缺少输入的变异验证并完成完整持续测试。

## 进一步优化的边界

更新的1000次局部输入profile里，原小地图的 NRGBA→RGBA重复分配已消失；仍有不可变图片、绘制指令、布局结果与匹配结果的分配，以及原生提交/内存管理成本。原生调用占比较高，但这个profile也包含初始化，不能直接把百分比当作逐帧成本。要进一步显著提速，需要单独评估可更新的GPU图片/纹理、绘制列表复用、增量排版等架构改动；这些需要跨CPU/GPU后端的生命周期和像素验证，不能用关闭显示功能或放松预算替代。没有宣称已经达到绝对性能上限。
