# 代码编辑器 里程碑 1 验收记录（规格 6.6 性能实测）

日期：2026-11-13。对应规格：`docs/specs/code-editor.md` 第 6.6 节。

## 测量环境与方法

- 机器：Apple M4（10 核），16 GB，macOS（Darwin 25.6），Go 1.27.2，`GOMAXPROCS=10`。
- 负载：共享机器，每组基准运行前的 `uptime` 1 分钟负载为 2.1–3.4（均 < 6）。下表是修订后（第 1 轮评审修正）的数字。
- 窗口：参考窗口 1920×1080 逻辑像素；除注明 `scale1` 外均为 Retina 2 倍（3840×2160 设备像素）。
- 文档：生成的 TypeScript，1,000,000 行，100.5 MB（每行约 100 字节，涵盖关键字、字符串、模板字符串、数字、注释）；第 4 行的场景用同一生成器生成的 2 万行 TS。
- 管线：`ui.Runner`（输入 → 构建 → 布局 → `editor.View` 绘制）+ `gpu.Renderer` + Metal 离屏设备。**一帧耗时 = `Runner.Frame`（CPU，含编码并提交命令缓冲）+ 等待 GPU 完成该帧**（`cpu-ms` / `gpuwait-ms` 分列）。帧不受显示器 vsync 节拍限制，fps = 1000 / 平均帧耗时，表示管线可持续的吞吐。
- 语法高亮在所有场景下保持开启（规格要求大文件不关闭高亮）。
- 测试文件由子测试进程（`TestPerfGenFile`）写到 `$TMPDIR/tango-editor-perf` 并复用，生成过程不进入被测进程的堆和 RSS。打开基准读的是**已在页缓存中的文件**（热读）。本机 `purge` 需要 sudo，冷读没测；按内置 SSD 顺序读约 3–6 GB/s 估算，100 MB 冷读多 20–35 ms，打开仍远低于 1 s。
- "后台高亮是否完成"用新增的只读查询 `highlight.Highlighter.Done(snap)` 判断（不移动 token 窗口、不分词）。之前用的 `Highlight(snap, n, 0)` 会把 token 窗口移到文末，让视图重新分词可见行。
- 复现：`ui/editor/perf_test.go` 文件头列出命令（如 `go test ./ui/editor -run '^$' -bench TypeAt1MLines -benchtime 300x`）；`TestPerfHostRenders` 校验离屏帧确实画出了带高亮的编辑器（截图核对过）。

**内存单位与归属。** 表中不带 i 的 MB 一律是 10^6 字节（基准 `perf_test.go` 的 `mb()` 按 1e6 换算，规格的"100 MB 文件"也是 100.5×10^6 字节 = 95.8 MiB）。`footprint(1)` 自己的类别明细按 1024 进位打印（"113 MB" 实为 113 MiB），表中引用时写作 MiB 并附换算。各数字的关系：
- `HeapInuse` 增量 158–165 MB 是 Go 分配器里正在使用的 span，**只有它叫"Go 堆"**；加上基线约 1 MB，绝对值约 165 MB = 157 MiB。
- "untagged (VM_ALLOCATE)" 211–213 MiB 是 footprint 里 Go 运行时（以及其他直接 mmap 的匿名内存）的脏页，**不是 Go 堆**：它包含 `HeapInuse` 约 157 MiB，其余约 55 MiB 是空闲但尚未归还的 span、GC 元数据、栈等（未逐项剖析）。同一行的 Reclaimable 列另有 105–108 MiB，不计入 footprint。修订前写的"Go 堆占 212 MB"把这一类别误称为 Go 堆，以此处为准。
- 图形 121.5 MiB ≈ 127 MB 在基线里不存在（基线时未建渲染目标），全部落在 footprint 增量中。footprint 增量减去图形：打开后约 260 MB，全文高亮后约 227–231 MB（2.3–2.6 倍）。

**内存口径（2026-11-13 用户已选定：Go 堆增量）。** 规格写的是"内存 ≤ 文件大小的 3 倍"，没说是哪种内存。按 Go 堆算是 1.6 倍，达标。按 RSS 算是 2.3–3.4 倍，在线上波动。按 phys_footprint 算是 3.5–3.9 倍，**不达标**；减去图形内存后是 2.3–2.6 倍。phys_footprint 包含了 Retina 全窗口的 GPU 渲染目标和字形图集，这部分约 127 MB（121.5 MiB），按 footprint 的类别归属推断与文件大小无关（没有单独测空文档窗口）。另外，修订前的报告写的是"堆 123 MB"，那是因为当时测试文件在被测进程里生成，基线被抬高了约 35 MB，那个数字偏低，以本表为准。建议的口径是"文件相关内存 = Go 堆增量"，GPU 内存另设窗口级预算（规格 6.8）；也可以选"phys_footprint 减去空文档窗口的 footprint"。用户选定第一种：本行按 Go 堆增量验收，1.6 倍，达标；进程 footprint 与 GPU 内存不计入本条门槛，另按规格 6.8 的窗口级预算考核。

## 终审修正（2026-11-13）

- **同帧输入顺序。** View 改用 `Context.EventsFor` 按到达顺序消费按键与已提交文本（同一个 `applyEvents`），同一帧内"Backspace 再输入 a"得到 `xa`，不再是先文本后按键；Shift+点击改用 `Context.PressMods`；窗口失去键盘焦点时光标隐藏、不再请求闪烁定时帧。
- **从右到左文字。** 与 Monaco / VS Code 一致：每行的基方向固定为从左到右、行从左边开始，希伯来文、阿拉伯文片段在行内按 bidi 重排（`// שלום x` 的 `//` 留在左边），不再按段落方向右对齐（含输入法组字路径）。左右方向键仍按逻辑顺序移动（里程碑 1）。
- **光标远在屏外时的 token 窗口。** 光标行不可见时，输入法候选窗位置改用光标行上次绘制时的 x（光标移动后未绘制过则用列网格估算），不再为它排版光标行，因此不再每帧移动高亮器的 token 窗口（见上表 `ScrollCaretFar`）。

## 瓶颈与里程碑 2 的应对

各项都有明显余量（内存按 Go 堆增量验收）。下面这些是余量的主要消耗，按影响排序：

1. **帧内高亮预算在"追赶"时每帧都被用满。** 可见区上方还有未分词的行时（刚打开文件就跳到中间、在 100 万行中间打字），`Highlight` 从第一个脏行开始分词，每帧花满 3 ms 的 `highlightBudget`，可见行却要等后台推进到那里才成为最终结果（100 万行要 13 s）。证据：第 50 万行打字 `cpu-ms` 3.7，全文高亮后 1.5。**应对：** 第一个脏行离可见区超过一定行数（比如 2,000 行）时，帧内不再从头追，只用猜测起始状态做显示 token，追赶交给后台；或者按检查点（每 N 行存一次状态）让后台从可见区附近开始，并以跳跃方式推进；后台在跑时调低帧内预算。
2. **每帧整帧重绘。** 里程碑 1 的 View 不发 `Damage`/`ScrollRegion`，而且 GPU 渲染器目前也忽略这些提示：2x 下每帧 GPU 等待 1.9–2.7 ms，占输入/滚动帧耗时的 35–45%。**应对：** GPU 里程碑 2 支持局部重绘后，View 在打字时只发光标行与行号的 Damage，滚动时发 ScrollRegion 加新露出的行；预计打字帧的 GPU 部分降到 1 ms 以内，滚动帧的 CPU 绘制也只剩新露出的几行。
3. **全文后台高亮的吞吐。** 约 13 µs/行（Monarch 解释器 + 混合正则），2 万行 0.27 s 远低于门槛，但 100 万行要 13 s，期间远处的 token 是猜测的。**应对：** 剖析 Monarch 解释器热点（规则匹配的正则缓存、按首字符预筛规则）；对行数极大的文档用多个 goroutine 按检查点并行推测分词，状态对上再合并。
4. **内存。** (a) 文本以外还有约 58 MB 的 Go 堆（158 MB 减去 100 MB 原文）：行索引、高亮器每行的状态和脏标记（每行约 5 字节，约 5 MB），以及打开时 `os.ReadFile` 的 []byte 和 `string(data)` 拷贝留下的碎片。还没有逐项剖析。(b) Go 运行时在 FreeOSMemory 之后仍保留 105–108 MiB（约 110–113 MB）可回收页（footprint 中 untagged 那一项的 Reclaimable 列，不计入 footprint），另有约 55 MiB 计入 footprint 的非 `HeapInuse` 脏页（见"内存单位与归属"）。(c) GPU 渲染目标和图集约 127 MB（121.5 MiB），与文件大小无关。**应对：** 用 `go test -memprofile` 剖析打开后的常驻对象；提供 `buffer.NewFromBytes`（接管 []byte、不拷贝），省掉打开时多出的 100 MB 峰值；超大文件用 mmap 只读原文；GPU 内存放到窗口级预算里优化（比如非 Retina 回退、图集按需收缩）。
5. **首次打开的冷开销。** 5 次打开里最差 109 ms，是新 Renderer 的空字形图集与首次上传（规格 6.8 冷启动另行验收）。**应对：** 进程内复用 Renderer/图集；字形图集预热常用 ASCII。
6. **测量本身的局限。** 无头基准不受 vsync 节拍限制；实机窗口的帧间隔（`-auto` 模式）这次没测成（见下面的实机检查）。

**补测中发现并修复的缺陷：Cmd+D 在大选区或含非法 UTF-8 的选区上 panic。** 第 5 项第一次测时，模拟工具发完 Cmd+↓ 后 Cmd 修饰键状态没有清掉，后面的字母变成了快捷键，选区变成了整篇文档（100.5 MB），再触发了 Cmd+D（`editor.action.addSelectionToNextFindMatch`）。`findSessionNow` 对选中的文本执行 `regexp.MustCompile("(?i)" + QuoteMeta(text))`，报 "expression too large" 后 panic。框架兜住了这次 panic，但那一帧没有画出来，日志里 panic 信息有 245 MB。实测编译这个正则的代价：100 万字符约 85 ms、分配 227 MB；1000 万字符约 720 ms、分配 2.3 GB；3000 万字符直接失败。对拍中还发现，只要选区里有非法 UTF-8 字节，哪怕很短，`regexp` 也会拒绝编译，同样会 panic。修复（`ui/editor/cursors.go`）：选区不超过 `findRegexpMax`（64 KiB）且能编译时仍用正则；否则改用 `foldIndex` 逐字比较，它和 `(?i)` 用的是同一套简单大小写折叠（与 `strings.EqualFold` 相同），非法字节只和完全相同的字节匹配。测试 `ui/editor/find_fold_test.go`：长选区不再编译正则，大小写不同、含 K 和 ſ 这类非 ASCII 折叠的匹配都能找到；非法 UTF-8 的选区可以用；另外与 `regexp` 做了 2 万组随机对拍，结果一致。修复后实机重做"100 万行 Cmd+A 再 Cmd+D"，没有 panic，从按键到截图完成 0.64 s。模拟工具也已改为打字事件显式清空修饰键。
