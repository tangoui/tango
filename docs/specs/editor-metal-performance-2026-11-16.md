# 编辑器第三轮性能优化实测（2026-11-16）

基线为第二轮已合并的 `e260df5`。保留现有 UI、完整高亮、小地图字符、缩进参考线、撤销和编辑语义。本轮主要收益是减少持续操作后的存活 Go 堆，以及图片纹理创建成本；整帧耗时没有统一提速。

## 改动

- 小地图替换或丢弃私有不可变条带时，立即通知渲染器移除旧图片缓存，避免继续保留数百帧。覆盖编辑替换、移出视口、字形/采样改变、关闭字符和关闭小地图。
- 新增可选 `Context.InvalidateImage(image.Image)`，由 Runner 接到渲染器；宿主同时转发给 GPU、永久 CPU 回退和临时超大画面 CPU 回退。无此能力的渲染器忽略提示。它必须在 UI goroutine、Render 前调用；原位修改像素还需要声明 Damage。图片像素仍由调用者持有，旧绘制列表以后仍能重新准备并绘制同一图片。
- Metal 等待上一批提交完成后，将本帧释放的同尺寸 RGBA8 ShaderRead 纹理转交给本帧新图片；同 ID、同尺寸完整上传也保留纹理。候选上限32个、8 MiB，剩余资源在所有返回路径释放，没有跨调用的空闲纹理池。尺寸不匹配时可能暂时多持有最多8 MiB，返回前释放。
- 逻辑图片 ID、完整像素上传顺序、缓存预算和错误策略保持原有约定。额外尺寸元数据随图片释放和设备关闭清除。
- API 生成器同时补齐基线已有实现、但旧清单缺失的 `text.ShapeInto` 和 `text.TrimFontCaches`；没有修改两者实现。

## 持续操作的存活内存

相同持续工作量：完整功能开启，输入1200次（每40次含 Enter），再来回滚动1800次。每阶段验证精确文本、字节数、行数；每次滚动必须实际移动，且小地图、高亮和参考线存在。旧新两次功能检查均通过。

下表是各阶段主动 GC 后的 **Go HeapAlloc**，不是进程总 RSS，也不包含全部 GPU/驱动资源。

| 阶段 | 修改前 MiB | 修改后 MiB |
| --- | ---: | ---: |
| 预热 | 22.39 | 22.28 |
| 累计400次输入 | 48.62 | 26.73 |
| 累计800次输入 | 52.63 | 30.53 |
| 累计1200次输入 | 56.10 | 34.09 |
| 再滚动600次 | 43.13 | 26.71 |
| 再滚动1200次 | 43.10 | 26.74 |
| 再滚动1800次 | 43.06 | 26.74 |

输入结束时减少约39.2%，滚动结束时减少约37.9%。撤销历史继续保留，输入期间增长符合测试工作量；不能据此证明所有工作负载没有泄漏。父进程还异步采样 RSS，1200次输入后约155 →114 MiB；采样时点不严格同步，只作辅助观察。两份记录最后的 RSS=0 表示子进程已退出，是无效样本，已排除。

## 原生 Metal 组件对比

Apple M4 / macOS arm64 / Go 1.27.2 / GOMAXPROCS=10。每轮300次操作，旧新交替5轮并交换先后，以下各指标独立取中位数。纹理微基准固定 OS 线程，每次使用 autorelease pool。小画面基准包含实际 Execute 和 Wait，并正确更新绘制批次的图片 ID。

| 场景 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 纹理替换 `applyImages` | 6.239 µs/op | 0.583 µs/op |
| 纹理替换临时分配 | 960 B，39次/op | 272 B，11次/op |
| 小画面整体 | 0.490 ms/op | 0.404 ms/op |
| 小画面提交段 | 0.1228 ms/op | 0.0852 ms/op |
| 小画面 GPU 等待 | 0.3672 ms/op | 0.3332 ms/op |
| 小画面临时分配 | 6826 B，239次/op | 6138 B，211次/op |

纹理替换组件耗时约降低90.7%，小画面提交段约降低30.6%。这些数字不能直接换算成整个编辑器同等幅度的提速。先前仅做原生复用时，编辑器旧图片仍在缓存中，效果有限；即时退役消除了这种资源滞留。

## 真实编辑器整帧对比

1920×1080逻辑尺寸、2×离屏 Metal、2万行 TypeScript、预先完成全文高亮，完整功能开启。每项1000次操作，逐项旧新紧邻交替3轮；以下指标独立取中位数。

| 场景 | 整帧 ms：前 → 后 | Runner.Frame CPU ms：前 → 后 | GPU等待 ms：前 → 后 | 临时分配 B/op：前 → 后 | 分配次数/op：前 → 后 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 输入，局部重绘 | 1.799 →1.919 | 0.909 →0.972 | 0.898 →0.931 | 364041 →364473 | 3291 →3274 |
| 滚动，局部重绘 | 3.527 →3.494 | 1.161 →1.112 | 2.357 →2.354 | 299673 →298877 | 3704 →3680 |
| 输入，完整重绘 | 4.006 →4.297 | 1.302 →1.356 | 2.705 →2.982 | 383788 →383649 | 3993 →3973 |
| 滚动，完整重绘 | 5.847 →5.680 | 1.688 →1.593 | 4.147 →4.085 | 283547 →283178 | 3315 →3293 |

输入整帧样本约慢6.7% /7.3%，滚动约快0.9% /2.9%，因此不能声称所有场景更快。Runner.Frame 列是该调用区间计时，不含之前派发输入事件；包含其间的系统调度影响。额外记录的进程 user+system CPU 包含初始化，局部输入1.392 →1.444秒、局部滚动1.649 →1.604秒、完整输入1.775 →1.829秒、完整滚动2.242 →2.124秒，也没有统一下降。

机器同时有其他活动，GPU等待和调度噪声明显。保留全部结果，没有以组件微基准替代整帧证据，也没有用最后较快样本替换较慢样本。本轮支持内存滞留与原生图片生命周期成本的改善，普通输入时延还需要隔离机器继续分析。这些均为离屏操作到 GPU完成的测量，不是物理输入延迟或显示器 FPS。

追加1000次局部输入 CPU profile仍能看到 `applyImages/newTexture` 的原生调用成本（累计0.36秒，样本总计1.12秒），以及提交、词法和内存分配。该 profile包含初始化，采样量小且机器共享，不能拿百分比当逐帧改善幅度；同帧同尺寸复用也不覆盖所有新建纹理，尚有进一步分析空间。

## 正确性与验证

- 原生测试持有旧纹理的额外 retain，排除释放后地址碰巧复用造成的假阳性。覆盖同帧/同 ID复用、尺寸不匹配、下一帧不保留、超限释放、32个/8 MiB边界、多个同时存活图片互不共享、重复/缺失释放、无效上传/恢复、重复关闭、带填充行距和预乘 alpha像素。
- 小地图集成测试检查设备图片数等于当前条带数，并对编辑、主题、缩放、字符开关、小地图开关逐步验证。旧图片像素保持不可变，退役后回放旧列表仍逐像素匹配 CPU参考（容差1）。宿主 GPU、永久 CPU回退、超大画面回退的缓存刷新均有像素回归。
- 原生复用、小地图退役、三种宿主缓存测试都先观察到基线失败，再验证修复后通过。
- Metal完整测试，编辑器/全部子包、宿主和示例完整测试通过；API清单检查、vet通过。
- 仓库短模式回归 `go test -p 1 -short -timeout 20m ./...`通过，129个有测试的包；完整 gallery文字对比扫描由 CI独立运行，本轮未重复。
- 竞态检查通过：Metal图片生命周期（2.174秒）、编辑器全部 `TestMinimap*` 与 `TestViewDamageVerified*`（157.166秒）、宿主三条缓存刷新路径（1.852秒）。示例构建、gofmt检查与 `git diff --check`通过。
- 独立只读审查未发现 Critical / Important / Minor问题。审查后只增加旧列表回放测试，没有修改生产代码。没有实施真实硬件设备丢失注入；原有故障处理策略不变。畸形上传参数的既有校验边界未扩大。
