# 编辑器第四轮性能优化实测（2026-11-16）

基线 `7454931`。继续保留全部编辑功能、UI和像素行为。本轮针对小地图条带宽度反复变化时的 Metal纹理分配，采用严格限额的同尺寸空闲纹理复用。代价是最多额外保留1 MiB名义 RGBA像素容量，另有原生对象和驱动开销；这不是新一轮内存下降。

## 调查与实现

新增可选 `TestEditorWarmInputProfile`：打开/高亮2万行 TypeScript、聚焦并移动光标后才开始采样，接收1000次真实按键。精确校验插入文本、字节数和行数，保留高亮、小地图和参考线。初次观察1414次图片上传，797次存在同帧同尺寸复用机会，其余尺寸变化仍需分配。另一份相同工作量观察1404次条带图片替换，逐字节相同的替换为0，拒绝了“重复上传相同图片”的假设。

没有扩大源图片、修改采样或着色器。Metal只复用已经等到前序提交完成、从逻辑 ID分离的同尺寸 RGBA8 ShaderRead纹理；当前帧候选优先，再查小型空闲池，上传仍完整覆盖每个像素。旧不可变图片值和绘制列表保持可重放。

空闲池最多16张纹理、1<<20名义像素字节，FIFO淘汰，超过120次后续 applyImages调用过期；非空执行帧没有图片上传时清空。没有继续渲染时仍可能留下最多这部分容量。原来的32张/8 MiB同帧暂存上限独立存在，未扩大图片缓存预算。

同步原生失败、GPU失败、图片参数错误和 Close释放空闲纹理。`gpu.Renderer.Trim`调用设备可选 `TrimImages`能力，立即释放空闲池，并禁止下一次图片处理重新填充它；必要的同帧复用仍有效。没有该能力的设备保持原路径。宿主 Metal presenter直接持有该设备，所以现有低内存通知能到达它。零尺寸帧仍按既有约定跳过，不计算为执行帧。

## 原生组件实测

Apple M4、macOS arm64、Go1.27.2、GOMAXPROCS=10。旧新二进制紧邻交替5轮，交换先后；每轮300次操作，各指标独立取中位数。变尺寸基准循环14种214–240×64图片，包含实际 Execute和 Wait。

| 场景 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 变尺寸小画面整体 | 0.4432 ms/op | 0.3746 ms/op |
| 变尺寸提交段 | 0.1308 ms/op | 0.1017 ms/op |
| 变尺寸 GPU等待 | 0.3078 ms/op | 0.2727 ms/op |
| 变尺寸临时分配 | 6826 B，239次/op | 6163 B，212次/op |
| 既有固定尺寸小画面整体 | 0.3848 ms/op | 0.3697 ms/op |
| 既有固定尺寸提交段 | 0.0972 ms/op | 0.0961 ms/op |
| 既有固定尺寸 applyImages | 1.154 µs/op | 1.168 µs/op |
| 既有固定尺寸 applyImages分配 | 272 B，11次/op | 272 B，11次/op |

变尺寸小画面整体约减少15.5%，提交段约减少22.2%。固定尺寸原有快速路径的成本基本持平。组件基准不能代表整个编辑器同幅度提速。

## 整帧与实际 CPU

相同1920×1080逻辑尺寸、2×离屏 Metal、2万行 TS、全文预先高亮，全部功能开启。四项分别紧邻旧新交替3轮，每轮1000次操作；各指标独立取中位数。实际进程 CPU为 user+system，包含初始化；Runner.Frame列是墙钟区间，不含之前派发事件的时间。

| 场景 | 整帧 ms：前 →后 | Runner.Frame ms：前 →后 | GPU等待 ms：前 →后 | 进程 CPU秒：前 →后 |
| --- | ---: | ---: | ---: | ---: |
| 输入，局部重绘 | 2.504 →2.363 | 1.734 →1.692 | 0.767 →0.687 | 2.358 →2.301 |
| 滚动，局部重绘 | 2.902 →2.825 | 1.657 →1.620 | 1.192 →1.165 | 2.312 →2.228 |
| 输入，完整重绘 | 6.412 →6.011 | 2.644 →2.698 | 3.764 →3.309 | 2.776 →3.306 |
| 滚动，完整重绘 | 5.161 →4.776 | 2.326 →2.282 | 2.901 →2.491 | 2.861 →2.868 |

| 场景 | 临时分配 B/op：前 →后 | 分配次数/op：前 →后 |
| --- | ---: | ---: |
| 输入，局部重绘 | 363278 →365010 | 3253 →3261 |
| 滚动，局部重绘 | 300323 →300331 | 3691 →3688 |
| 输入，完整重绘 | 383694 →384075 | 3950 →3936 |
| 滚动，完整重绘 | 285032 →284744 | 3310 →3299 |

整帧中位数分别约少5.6%、2.6%、6.3%、7.5%，但不能据此声称所有场景持续提速：完整输入的实际进程 CPU反而约多19.1%，其单轮整帧从旧4.230/6.412/7.077 ms变为新4.924/10.057/6.011 ms，机器调度/负载变化很大。完整滚动也有一轮变慢。临时分配总体基本持平。

匹配的预热后诊断 profile中，newTexture累计样本0.27 →0.10秒，总样本1.10 →1.14秒。原生纹理分配热点减小，其他 tokenization、提交和内存工作仍显著；这只是两份小样本，诊断设备也带有统计开销，不能把百分比当成逐帧时延收益。最初不含额外条带比较的 profile另存于 before目录，不与这组数字混用。

为核实完整输入的 CPU增加，完成所有重检查后，使用最终错误清理修复后的二进制，按固定1500次输入、旧新交替3轮追加复测，数据独立保存，没有替换首轮结果：

| 轮次 | 实际进程 CPU秒：旧 →新 | 整帧 ms：旧 →新 |
| --- | ---: | ---: |
| 1 | 3.998 →3.399 | 7.846 →7.355 |
| 2 | 4.841 →4.342 | 9.306 →9.096 |
| 3 | 4.381 →2.688 | 8.106 →5.221 |

进程 CPU中位数4.381 →3.399秒，未复现首轮 CPU增加；整帧与 Runner.Frame中位数8.106 →7.355 ms、2.659 →1.946 ms。它们和首轮工作量不同，不能直接合并；前后变化方向不稳定仍说明机器噪声明显。这支持保留有明确纹理复用/组件分配收益的实现，但不构成所有场景稳定提速的证明。

离屏完成耗时不是物理键盘到屏幕延迟或显示器 FPS；共享机器结果不能替代隔离环境的稳定时序结论。

## 持续操作与内存

旧新分别真实输入1200次，再来回滚动1800次，均通过精确内容、行数、实际滚动及显示功能断言。GC后 Go HeapAlloc如下，不含全部原生 GPU/驱动资源：

| 阶段 | 修改前 MiB | 修改后 MiB |
| --- | ---: | ---: |
| 预热 | 22.39 | 23.44 |
| 累计400次输入 | 26.73 | 26.73 |
| 累计800次输入 | 30.53 | 30.35 |
| 累计1200次输入 | 33.99 | 33.98 |
| 再滚动600次 | 26.77 | 26.77 |
| 再滚动1200次 | 26.74 | 26.78 |
| 再滚动1800次 | 26.77 | 26.74 |

持续操作结束的 Go堆基本一致，保留上一轮及时退役图片的收益。预热时点缓存/前台工作尚有变化，不能把约1 MiB的 Go堆差异归因于名义 GPU池容量。异步 RSS采样仅辅助观察；最后的0表示进程已退出，排除为无效样本。没有声称进程总内存未增长，也没有声称覆盖所有工作负载。

## 验证与复现

原生身份测试额外 retain旧对象，排除释放后地址偶然复用。覆盖跨帧变尺寸回归、完整颜色/预乘 alpha/带填充行距覆盖、16张/1MiB边界与 FIFO、多个同时存活 ID不共享、无上传清理、过期、无效上传恢复、同步/GPU错误、低内存即时清理与下一帧不回填、重复 Trim/Close及关闭后调用。核心复用/边界和错误/Trim路径分别观察到 RED，再验证 GREEN。

- 完整 GPU包族回归通过，修复后的 Metal11.956秒、shader20.763秒；UI、编辑器及全部子包、宿主、示例完整回归通过（editor140.937秒）。
- 仓库短模式 `go test -p 1 -short -timeout 20m ./...`最终通过，129个有测试的包；完整 gallery文字对比扫描按 CI独立任务，本轮未重复。
- 首次仓库短测的 `TestMatchManyCursorsBounded`失败于现有2.75 ms墙钟门限（6帧超时）。在与编译并行的单独复测中也出现一次门限失败，这组有干扰，不能用于代码速度归因。停止重工作后，预编译旧新二进制严格串行交替各10次均通过；最终完整仓库短测也通过。保留失败日志，未修改括号实现或放宽门限。
- 竞态通过：Metal图片生命周期/Wait错误（1.965秒）、renderer图片/Trim（1.793秒）、编辑器旧小地图图片释放/回放（5.220秒）。API82份清单、vet、构建、gofmt、diff检查通过。
- 诊断测试的缺少按键派发变异被精确内容断言拒绝，确保测量实际工作量。
- 独立只读审查提出1项重要问题：stage和ReadPixels的原始分配/命令创建错误分支绕过既有错误计数入口，也漏清空闲池。测试使用真实原生 nil receiver使分配/命令返回空对象，三个分支先 RED，再经仅增加清理的修复 GREEN；原错误计数、pending/lost策略明确断言不变，随后完整 GPU及仓库短测通过。没有未处理的严重/重要/次要审查项。
- 没有真实硬件设备丢失注入；使用现有错误注入入口验证清理与原有故障策略。物理延迟和完整驱动内存没有测量，不作相关结论。
